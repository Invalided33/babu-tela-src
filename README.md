# Babu Tela

Chat de comunidades com texto, voz, vídeo, compartilhamento de tela e música em grupo, para Windows. Tudo é **Rust**: o app desktop (interface nativa desenhada com [egui](https://github.com/emilk/egui), sem navegador embutido nem JavaScript), o servidor na Cloudflare (WebAssembly), o instalador e as ferramentas de build. Não há versão para navegador: o endereço do servidor só mostra onde baixar o app.

O servidor roda na **Cloudflare**, então não depende de nenhum computador ligado em casa: os amigos baixam o app na [página de download](https://invalided33.github.io/babu-tela/) e entram com a conta do Google. As mensagens, os anexos e as chamadas são cifrados de ponta a ponta: nem quem tem a conta da Cloudflare e a do Google lê o que as pessoas dizem (veja "Privacidade").

## O que você precisa

- Rust estável, pelo [rustup](https://rustup.rs).
- Visual Studio Build Tools com "Desenvolvimento para desktop com C++", incluindo as "Ferramentas do CMake para Windows". O codec de voz (libopus) é compilado com esse CMake; o `cargo xtask` acha ele sozinho. Para rodar `cargo` direto, ponha o CMake no PATH.
- [NASM](https://www.nasm.us), para as rotinas em assembly dos codecs de vídeo: sem ele o decodificador de AV1 (rav1d) não compila, e o openh264 sairia em C++ puro, levando uns 24 ms para codificar uma imagem em vez de 4. O `cargo xtask` acha o NASM no PATH ou em `%LOCALAPPDATA%\Programs\NASM`; para rodar `cargo` direto, ponha o NASM no PATH. Se ele for instalado depois de um build, rode `cargo clean -p openh264-sys2` para o openh264 ser compilado de novo.

O resto (o alvo `wasm32-unknown-unknown` e o `worker-build`) o `cargo xtask servidor` instala na primeira vez.

## Na Cloudflare

Uma vez só, crie `build/cloudflare.json`. Ele guarda as chaves e nunca entra no git:

```json
{
  "contaId": "id da conta Cloudflare",
  "apiToken": "token de API",
  "worker": "babutela",
  "endereco": "https://babutela.SUA-CONTA.workers.dev",
  "bucket": "babutela",
  "r2AccessKeyId": "",
  "r2SecretAccessKey": "",
  "armazenamentoGb": 10,
  "segredos": {
    "PEPPER": "64 caracteres aleatórios",
    "TEST_HUB": "outro valor aleatório",
    "GOOGLE_CLIENT_ID": "",
    "GOOGLE_CLIENT_SECRET": "",
    "TURN_KEY_ID": "",
    "TURN_KEY_TOKEN": "",
    "GIPHY_API_KEY": ""
  }
}
```

1. **`apiToken`**: um API token com permissão de editar Workers e de ler e escrever no R2.
2. **`PEPPER`** assina os bilhetes de envio de arquivos. **`TEST_HUB`** libera o banco separado que os testes usam (e as contas de teste, que só existem lá). Guarde uma cópia do arquivo.
3. **`GOOGLE_CLIENT_ID`** e **`GOOGLE_CLIENT_SECRET`**: o login, que é só com o Google. Uma vez só, no [Google Cloud Console](https://console.cloud.google.com):
   1. Crie um projeto.
   2. Em **Google Auth Platform** → **Branding**, dê o nome do app e o e-mail de suporte. Em **Audience**, escolha **External** e clique em **Publish app** (em produção). O app só pede nome e e-mail (`openid`, `email`, `profile`), então não precisa da verificação do Google; em "Testing", só os e-mails de teste conseguiriam entrar.
   3. Em **Clients** → **Create client**, escolha **Desktop app** e copie o ID e o segredo para estes dois campos. O segredo fica só no Worker; o app nunca o vê.

   Sem eles o app abre, mas ninguém consegue entrar.
4. **Ative o R2** no painel (R2 Object Storage). É o único passo que a API da Cloudflare não faz: o plano gratuito pede um cartão, mas não cobra nada até 10 GB. Depois disso o `cargo xtask servidor` cria o bucket com o nome de `bucket` sozinho. Sem ele o chat funciona, mas enviar arquivos e a atualização automática não.
5. **`r2AccessKeyId`** e **`r2SecretAccessKey`** (opcionais): chaves de API do R2, só para o `cargo xtask publicar`. Vazias, ele usa o próprio `apiToken` como chave do R2, como a Cloudflare permite (o id do token e o SHA-256 dele).
6. **`armazenamentoGb`** (opcional): quanto os anexos podem somar, em GB. Sem ele são 10, o que o R2 dá de graça, então os arquivos nunca geram cobrança de surpresa. `0` tira o teto.
7. **`TURN_KEY_ID`** e **`TURN_KEY_TOKEN`**: uma chave TURN (painel → Realtime → TURN), o relé para duas pessoas que não conseguem se ligar direto. Sem ela as chamadas usam só STUN, o que funciona em boa parte das redes.
8. **`GIPHY_API_KEY`**: a chave das figurinhas, de um app criado em [developers.giphy.com](https://developers.giphy.com) do tipo **API**, não SDK. Os SDKs do GIPHY são bibliotecas com interface pronta para iOS, Android, web, React Native e Flutter, e a chave SDK fica sob o contrato do SDK; o Babu Tela desenha a própria interface e fala direto com a API, que é o caso da chave API (e dos termos da API). O servidor entrega a chave aos apps quando eles conectam (o GIPHY exige que os pedidos saiam do app), então trocar a chave não pede versão nova do app. Vazia, o botão de figurinhas some. A chave começa como "beta": 100 pedidos por hora para todos os usuários juntos (veja "Limites conhecidos"). Para passar disso, no painel: "Upgrade to Production" na chave, com imagens do app (o `cargo xtask medir figurinhas --giphy` guarda uma em `build/giphy/`); o GIPHY revisa e combina o preço.
9. **`pagina`** (opcional, fora de `segredos`): o repositório da página de download, como `"dono/repositorio"`. Sem ele é `babu-tela`, na conta em que o GitHub CLI está conectado.

`REALTIME_APP_ID` e `REALTIME_APP_SECRET` eram do SFU, que não existe mais. Se ainda estiverem no arquivo, o `cargo xtask servidor` não os envia e os apaga do Worker.

O `cargo xtask servidor` cria o Worker na primeira vez; o banco nasce junto com ele. **Não apague o Worker no painel**: o banco vive dentro do Durable Object dele, então apagar o Worker apaga contas e mensagens junto, sem volta. Para trocar o código, basta rodar `cargo xtask servidor` de novo.

## Comandos

Tudo passa por `cargo xtask` (o crate `crates/xtask`):

| Comando | O que faz |
|---|---|
| `cargo xtask dev` | Abre o app em modo de desenvolvimento |
| `cargo xtask servidor` | Compila o servidor para WebAssembly, publica na Cloudflare e grava os segredos |
| `cargo xtask testar` | Testes em Rust (app, instalador, ferramentas e servidor) e depois os de ponta a ponta contra o servidor publicado, num banco de teste separado. `--so-servidor` pula os primeiros |
| `cargo xtask chamada` | Uma chamada de verdade entre 2 a 6 cópias do app neste PC (veja "Testes") |
| `cargo xtask direto` | Um arquivo grande com "Enviar direto" entre duas cópias do app neste PC, sem passar pelo servidor (veja "Testes") |
| `cargo xtask medir` | Mede o atraso, o processador e a memória do app otimizado neste PC, contra o servidor publicado, e guarda os números em `build/medidas/` (veja "Testes") |
| `cargo xtask chave` | Cria, na primeira vez, a chave que assina as atualizações (veja "Privacidade"), em `%USERPROFILE%\.babutela\chave-atualizacoes.txt` (ou no arquivo de `BABUTELA_CHAVE_ATUALIZACOES`), fora do `build/cloudflare.json` e da Cloudflare, e mostra a parte pública. Depois disso só mostra onde ela está. O `release` e o `publicar` não rodam sem ela. Guarde uma cópia longe deste PC: sem ela, nenhuma versão nova chega aos apps instalados, que teriam de ser instalados de novo à mão |
| `cargo xtask assinar VERSÃO SHA256` | Para quando mais de uma pessoa assina as atualizações (`assinantes.txt`, veja "Privacidade"): mostra a assinatura deste PC para aquele instalador, uma linha que quem publica põe em `build/assinaturas/<versão>.txt`. Assine só um instalador que você mesmo compilou e conferiu (o mesmo SHA-256) |
| `cargo xtask release` | Gera `build/release/Babu Tela Setup.exe`, o instalador que todos usam, com as partes públicas das chaves das atualizações dentro do app (a deste PC, ou as de `assinantes.txt`, com o mínimo de assinaturas). `--endereco https://outro.servidor` aponta para outro servidor |
| `cargo xtask release update` | Lança uma versão nova inteira: o instalador, o servidor (com a lista de emoji), a atualização automática e a página de download |
| `cargo xtask publicar` | Envia o instalador de `build/release` para a atualização automática dos apps já instalados, com o `latest.json` assinado pela chave deste PC e pelas de `build/assinaturas/<versão>.txt` (sem o mínimo, não envia), e põe a versão no registro público |
| `cargo xtask pagina` | Põe o instalador de `build/release` na página de download (GitHub Pages) |
| `cargo xtask emoji` | Copia a lista oficial de emoji do Unicode e os nomes em português do CLDR para o servidor (`<endereco>/emoji/`), de onde os apps a leem. Confere cada arquivo antes de enviar e só envia o que mudou. Rode de novo quando sair uma versão nova do Unicode (todo setembro) |
| `cargo xtask modelo` | Diz se a Ceva publicou no Hugging Face um modelo novo da supressão de ruído (o DPDFNet que vai no app, fixado numa revisão em `crates/denoise/model/NOTICE`). `--atualizar` traz o novo: baixa na revisão nova, confere o SHA-256, guarda os pesos em float16, confere que a cópia dá o mesmo som que o original, roda os testes do denoise e reescreve o `NOTICE`; se algo falhar, o modelo de antes fica |
| `cargo xtask icones` | Redesenha os ícones da interface (`crates/app/assets/icons/`) |

Para lançar uma versão nova: aumente a versão em `Cargo.toml` (`[workspace.package]`, o único lugar) e rode `cargo xtask release update` (na primeira vez, antes, `cargo xtask chave`). Antes de compilar ele confere os segredos, o GitHub CLI (`gh auth login`) e que a versão é mais nova que a dos apps, e avisa se a Ceva publicou um modelo de ruído novo (sem parar por isso); depois gera o instalador, publica o servidor (o app e o servidor andam na mesma versão), atualiza a cópia da lista de emoji no servidor (se isso falhar, ele só avisa: os apps buscam a lista no Unicode enquanto isso), envia o instalador para a atualização automática e atualiza a página. Os apps instalados se atualizam sozinhos na próxima vez que abrirem (veja "Atualização automática"); os da 0.11.1 e anteriores ainda mostram "Reiniciar e instalar" uma última vez.

A **página de download** é um repositório público do GitHub só com ela (`index.html`, feito de `crates/xtask/pagina/index.html`, e o ícone), sem o código do app. O instalador vai numa versão (release) do GitHub desse repositório, e a página aponta para ele, com o tamanho, a data e o SHA-256. O `cargo xtask pagina` cria o repositório e liga o GitHub Pages na primeira vez, pelo token do GitHub CLI. A atualização automática continua no R2.

## Como funciona

O app só guarda o que é seu; tudo o que é compartilhado vive no servidor da Cloudflare.

- **Servidor e banco**: um [Durable Object](https://developers.cloudflare.com/durable-objects/) chamado `main`, com um SQLite próprio. Ele guarda contas, servidores, canais, mensagens e também as conexões abertas, então o chat inteiro é consistente.
- **Tempo real**: um WebSocket por app aberto. Entre mensagens o objeto pode dormir enquanto as conexões ficam de pé, então cada conexão carrega o que sabe sobre si mesma (quem é, status, se está numa chamada). O "ping" do app é respondido pela própria Cloudflare, sem acordar o servidor.
- **Mensagens sem espera**: quem envia vê a mensagem na hora, um pouco apagada até o servidor confirmar, com uma marca (`nonce`) que liga essa cópia à que o servidor devolve. Ela sobe pelo próprio WebSocket, sem a volta pelo Worker que um POST faz, e o objeto a manda para todos antes de gravar: uma gravação segura tudo o que o objeto envia até ser confirmada em outros data centers, e isso custava uns 40 ms a quem recebe; agora só a confirmação para quem enviou espera por ela. Se a cópia do servidor não volta em 3 segundos (ou a conexão cai), o app manda de novo por HTTP com a mesma marca, e o servidor reconhece a segunda tentativa em vez de duplicar a mensagem. Mensagens com arquivos e as maiores que 64 KB vão por HTTP.
- **Arquivos**: os anexos e os instaladores ficam no [R2](https://developers.cloudflare.com/r2/), servidos em `/uploads/` e `/updates/` direto pelo Worker, sem acordar o chat. Os anexos sobem já cifrados pelo app, com o nome `arquivo.bin`: o R2 só guarda bytes que não abrem sem a chave que vai dentro da mensagem (veja "Privacidade"). Um anexo sobe em partes (o multipart do R2, de 8 MiB para cima), seis de cada vez, lidas do disco aos pedaços enquanto sobem e enviadas direto para o bucket, então não há limite de tamanho além do próprio R2 (perto de 1 TB por arquivo) e nada fica inteiro na memória. Uma parte de cada vez deixava a linha parada enquanto o R2 respondia cada uma: um arquivo de 64 MB subia a 4,9 MB/s numa linha que aguenta 17; com seis, sobe no que a linha aguenta. Uma parte que falha é enviada de novo, a barra mostra o progresso, e o X cancela (a mensagem volta para a caixa de texto). O que somam todos os anexos tem o teto de `armazenamentoGb`.
- **Enviar direto**, para arquivos enormes, como no Keet: com "Enviar direto" ligado (embaixo dos arquivos anexados na caixa de texto; vem desligado e vale para todos eles), os arquivos não sobem para o servidor nem ocupam o R2. A mensagem leva só o que o arquivo é, cifrado como o resto dela: o nome, o tamanho, como ele é cortado em pedaços e o hash deles; o servidor guarda só um id para o arquivo. Quem pode ler a mensagem baixa do PC de quem enviou, por WebRTC (um canal de dados numa conexão só para isso, direto entre os PCs ou, se não der, pelo relé TURN), enquanto os dois estão com o app aberto. O servidor só leva os poucos recados que montam cada conexão (o `direct`, em `crates/worker/src/direct.rs`), selados e assinados para a outra pessoa, e só entre quem enviou e quem pode ler a mensagem.
  - **Pedaços e hashes**, como no BitTorrent: antes de enviar, o app lê o arquivo inteiro e calcula o SHA-256 de cada pedaço (de 4 MiB para cima, potência de 2, no máximo 32.768 por arquivo); a mensagem leva o hash de todos juntos, e a barra mostra "Preparando". Quem baixa recebe a lista dos hashes, confere com o da mensagem e confere cada pedaço que chega. Quem envia confere cada pedaço ao ler e só manda o último bloco dele depois de conferir: se o arquivo mudou desde que foi enviado, o download para e diz isso, em vez de juntar dois arquivos.
  - **Baixar**: quem baixa escolhe onde salvar. O arquivo vem para `<nome>.parcial` e ganha o nome quando está inteiro. Pausar, fechar o app ou a conexão cair não perde o que já veio: o que foi conferido é gravado no disco de verdade (`sync_data`) e anotado a cada 5 segundos, e o download continua dali. Se a conexão cai, ele tenta de novo em 3 segundos, até 5 vezes seguidas sem um pedaço a mais; se quem enviou está offline, espera e continua sozinho quando a pessoa volta (a presença e cada nova conexão com o servidor avisam), e "Tentar agora" tenta na hora. O cartão do arquivo mostra o progresso, a velocidade, o tempo que falta e se vai pelo relé, com Pausar, Continuar e Cancelar (que apaga o que veio); pronto, Abrir e Mostrar na pasta.
  - **Enviar**: o app de quem enviou manda para até 6 pessoas ao mesmo tempo (2 por pessoa); as outras esperam a vez já conectadas, e o cartão delas mostra "Na fila". O cartão de quem enviou mostra para quantas pessoas está mandando, e "Parar de compartilhar"; apagar a mensagem também para. As listas do que cada PC compartilha e baixa, com os hashes ao lado, ficam em `%LOCALAPPDATA%\Prosa\direto`, cada item marcado com a conta.
  - **O pedido**: assim que o canal de dados abre, quem baixa pede o arquivo de um pedaço em diante (e a lista dos hashes, se ainda não a tem), e quem envia manda. Esse primeiro recado chega mesmo quando sai no instante em que a conexão sobe (veja "WebRTC", abaixo).
  - Uma versão do app anterior a esta mostra o arquivo como um anexo comum, que abre a página de download do app.
- **Chamadas**: só entre as pessoas (P2P, em malha), sem servidor de mídia. Cada par tem a própria conexão WebRTC, com voz em Opus e vídeo/tela em H.264, ou em AV1 quando a placa de vídeo de quem compartilha a tela codifica AV1 e ninguém na chamada usa uma versão do app anterior à 0.11.3. O servidor só repassa a sinalização, selada e assinada para cada pessoa (veja "Privacidade"), e só entre quem está na mesma chamada. Como cada pessoa manda para cada uma das outras, o app economiza o upload de quem envia e o processador de quem recebe:
  - **Voz**: a taxa cai conforme a chamada cresce: 48 kb/s até 4 pessoas, 32 até 8, 24 até 16 e 20 acima disso. Até 4 pessoas os pacotes são de 10 ms (metade do som para esperar e metade da fila para guardar); de 5 a 8, de 20 ms; nas chamadas grandes, de 40 e 60 ms, porque cada pacote leva uns 50 bytes de cabeçalho (IP, UDP, RTP e SRTP), repetidos para cada pessoa. Com o DTX do Opus, quem está calado quase não manda nada.
  - **Fila de quem recebe**: guarda um pacote, a variação que a rede mostrou nos últimos 2 segundos e mais 10 ms. Quando sobra, ela encolhe aos poucos: tira trechos de silêncio, ou corta 10 ms com uma transição suave, sem picotar a voz.
  - **Vídeo e tela** saem em duas cópias: uma pequena (miniatura) e a da qualidade escolhida no seletor de compartilhar (que vale também para a câmera; trocada durante a transmissão, ela recomeça na nova). Quem assiste diz, por um canal de dados direto, qual cópia quer: a grande quando a imagem está ampliada ou num quadro grande, a pequena nos quadrinhos, e nenhuma quando não está olhando a chamada. Com muitas câmeras, só as 9 de quem falou por último chegam em vídeo; as outras mostram a foto e não gastam nada. Cada imagem é montada assim que o último pacote dela chega (o bit de marcação do RTP), sem esperar a próxima; um pacote perdido é pedido de novo (NACK), e uma imagem que não deu para montar pede uma imagem inteira (PLI).
  - **Congestionamento**: a cada meio segundo cada conexão mede, pelo canal de dados, o tempo de ida e volta e quantos pacotes de vídeo chegaram e quantos se perderam. (Os relatórios RTCP não servem: o webrtc-rs 0.21.1 não os repassa, e a perda e o atraso nunca chegavam ao app.) Se uma conexão engasga, aquela pessoa passa para a cópia pequena e só tenta a grande de novo depois de um tempo, que dobra a cada falha. Se a maioria engasga junto, é o upload de quem envia que acabou, e o orçamento de vídeo dele diminui. A voz sai sempre na frente, e o vídeo é espaçado para não atrasá-la.
  - **Relé**: quando duas pessoas não se alcançam direto (por exemplo, numa rede que bloqueia UDP), a conexão delas passa pelo relé TURN da Cloudflare, por UDP, TCP ou TLS (portas 443 e 80). As credenciais do relé são geradas na hora e expiram em 12 horas.
  - **Som da tela**: quem compartilha a tela manda junto o som do PC, se "Compartilhar o áudio" estiver marcado no seletor (vem marcado). É o loopback por processo do WASAPI, o mesmo que a captura de áudio de aplicativo do OBS usa (Windows 10 versão 2004 ou mais novo): a tela inteira leva todo o som do PC menos o do próprio Babu Tela, que é a chamada e voltaria para todos como eco; uma janela leva só o som do programa dela (e dos processos que ele abriu, como o de áudio do navegador). Vai numa trilha própria, separada da voz, em Opus estéreo a 96 kb/s, só quando há som. A trilha só vai para quem avisou, pelo canal de dados, que conhece esse som (uma cópia mais antiga do app tocaria como se fosse a voz), e não vai para quem silenciou a transmissão. Com várias telas na chamada, quem amplia uma ouve só o som dela; nos quadrinhos, ouve todas.
  - **Quedas**: a mídia vai direto entre as pessoas, então uma queda do WebSocket não derruba a chamada. Quando a conexão de alguém que está numa chamada fecha, o servidor guarda o lugar dele por 15 segundos (numa tabela do SQLite, porque o objeto pode dormir nesse meio-tempo, e com um alarme do Durable Object para o fim do prazo), junto com a sinalização que chegar para ele. Se o app volta nesse prazo, retoma o lugar e recebe essa sinalização, e ninguém vê a pessoa sair. Depois do prazo, o servidor a tira da sala, e os outros desligam a conexão com ela; quando ela volta, eles fazem conexões novas. Uma descrição (SDP) com outro certificado DTLS é sinal de conexão nova do outro lado, e a nossa é refeita também: o webrtc-rs 0.21.1 trataria a oferta nova como renegociação da antiga, reiniciaria só o ICE e ficaria com a associação DTLS antiga, que o outro lado não tem mais, e ninguém ouviria ninguém dali em diante. Uma conexão que falha de vez (ICE ou DTLS) também é refeita, e, quando o WebSocket volta, as que não estão de pé são refeitas, porque o que estava a caminho delas se perdeu na queda.
  - **Botões e tela cheia**, como no Discord: o microfone e o som ficam ao lado da engrenagem, embaixo de "Voz conectada"; a câmera, a tela e o desligar ficam embaixo da chamada. A tela cheia ("Tela cheia", no alto da chamada ou sobre a imagem de alguém) ocupa a tela inteira, por cima da barra de tarefas. Antes, a barra de tarefas ficava por cima: o app abre maximizado, e o winit prende uma janela maximizada sem moldura à área de trabalho da tela, que não inclui a barra (o Chromium tira a janela do maximizado antes da tela cheia pelo mesmo motivo). Agora a janela volta ao tamanho normal antes e é maximizada de novo na saída. Na tela cheia só aparece a imagem; os botões da chamada, todos e mais "Sair da tela cheia", aparecem por 3 segundos quando o mouse mexe, e o ponteiro some junto com eles. Esc também sai. "Parar de assistir", sobre a tela compartilhada de alguém, faz a imagem e o som dela pararem de vir (quem compartilha deixa de mandar), até "Assistir transmissão" ou até a pessoa compartilhar de novo.
  - **Volume de cada pessoa**: o botão direito em alguém (no quadro da chamada ou na lista da sala de voz) abre "Silenciar" e o volume da voz, de 0 a 200 %, e, enquanto a pessoa compartilha a tela, "Silenciar transmissão" e o volume do som dela. Vale só neste PC (os outros continuam ouvindo como antes), em todas as chamadas, e fica em `prefs.json`. Quem foi silenciado aparece com o alto-falante cortado, e a tela, com "tela sem som".
  - **Apresentação**, como o PowerPoint Live do Teams, mas com o arquivo em vez de um vídeo dele: em Compartilhar → Apresentação, quem apresenta escolhe um arquivo do PowerPoint (.pptx ou .ppsx) ou um PDF, e o app desenha os slides no PC dele, onde estão as fontes da apresentação. O .pptx é desenhado pelo [BetterOffice](https://github.com/openooxml/betteroffice) (Rust, Apache 2.0, dentro do .exe: 8,6 MB a mais nele) e o PDF pelo leitor do próprio Windows (`Windows.Data.Pdf`); ninguém precisa do PowerPoint. As fontes vêm do Windows, das que a pessoa instalou e das que o Office baixa para si (a Aptos, a fonte do Office desde 2023, só existe ali); a busca por elas começa quando o seletor de arquivo abre, porque a primeira depois de ligar o PC levou 3 s (as seguintes, 40 ms). Cada slide vira uma imagem de até 1920 × 1080, em PNG, ou em JPEG quando é foto e o JPEG sai com menos de dois terços do tamanho, e as imagens vão para os outros pelo canal de dados da chamada, de pessoa para pessoa: o slide da tela primeiro, depois os vizinhos (os da frente antes), em pedaços de 16 KiB, com no máximo 64 a 128 KB a caminho por vez, repartidos entre quem recebe, para não atrasar o resto do canal nem afogar uma conexão lenta. Trocar de slide é uma mensagem de poucos bytes. Quem assiste não precisa das fontes e não abre arquivo de ninguém: só decodifica imagens, cada uma reduzida no processador para o tamanho em que aparece (as texturas do egui não têm mipmaps, e um slide desenhado bem menor que a imagem tremeria). Quem apresenta vê o slide atual, o próximo, as anotações (só ele as vê), a fileira de todos os slides e um relógio, e passa os slides pelo teclado ou por um passador de slides (→, ↓, PageDown, espaço, Enter ou N para a frente; ←, ↑, PageUp, Backspace ou P para trás; Home e End para as pontas). Quem assiste segue quem apresenta, pode passar os slides sozinho e voltar com "Voltar ao apresentador", e amplia com a roda do mouse (até 4 vezes, arrastando para ver o resto) ou com os botões sobre o slide; "Ver pessoas" troca a apresentação pelos quadros de todos. Medido no app otimizado, com o modelo "Treinamento" do PowerPoint (19 slides, 3,8 MB de imagens) numa chamada de duas pessoas: abriu em 65 ms e desenhou os 19 em 3 s (157 ms por slide, num núcleo, com prioridade baixa), e as imagens chegaram a quem assistia junto com o desenho; a memória privada subiu uns 35 MB em quem apresentava (70 MB enquanto desenhava) e uns 45 MB em quem assistia, e o processador com a apresentação parada ficou igual. Contra a exportação do próprio PowerPoint, nos 54 slides dos modelos que vêm com ele, texto, tabelas, fotos e formas saem quase iguais (SSIM 0,96 em média); os gráficos mantêm os números, mas nem sempre as cores (veja "Limites conhecidos"). Uma cópia do app anterior a esta não diz que mostra apresentações, e não recebe nada.
  - **Anotação**, como no Zoom, no Teams e no Meet: sobre uma tela ou janela compartilhada, ou sobre o slide de uma apresentação, quem está na chamada desenha por cima ("Anotar", no canto da imagem ampliada ou do slide), e todos veem o traço enquanto ele é feito. As ferramentas são as que os três têm em comum: a tinta que some (a que vem escolhida, como no Meet: fica 1,5 s e some em 1 s, boa para apontar), a caneta, o marca-texto, a seta, o retângulo, a elipse e a borracha (que leva o traço inteiro), em 8 cores e 3 espessuras, com desfazer e refazer (Ctrl+Z e Ctrl+Y), limpar, e "Salvar imagem", que guarda em PNG o que está à vista com os traços e sem a barra. O nome de quem desenha aparece ao lado do traço por um momento. Quem compartilha decide quem anota ("Todos podem anotar" ou "Só eu posso anotar", como no Teams), pode apagar os traços de qualquer um, e guarda tudo o que foi desenhado: quem entra depois recebe os traços dele. Cada slide tem os seus. Os traços não vão no vídeo: cada app desenha sobre a imagem os pontos que chegam pelo canal de dados da chamada (posições de 0 a 1 na imagem, a cada 40 ms enquanto o traço é feito), então ficam nítidos em qualquer tamanho e não pesam na transmissão. Quem compartilha a tela vê os traços de todos sobre a própria tela, numa janela que o Windows deixa fora de qualquer captura (`WDA_EXCLUDEFROMCAPTURE`), para que não voltem no vídeo; no alto da tela compartilhada, uma barra que também fica fora da captura tem o "Anotar", que abre as ferramentas para desenhar direto na tela: enquanto uma ferramenta está escolhida, uma janela que não mostra nada pega o mouse, e o botão do ponteiro na barra ou o botão direito devolvem o mouse à tela. A barra pode ser arrastada. Sobre uma janela, tudo segue a janela e só aparece com ela na frente. Essa janela é desenhada no processador (tiny-skia), e só a parte que mudou: no app otimizado, desenhar a tela inteira de traços leva de 0,5 a 0,7 ms em 1080p e de 2,6 a 3,9 ms em 4K.
- **WebRTC**: as chamadas e os arquivos diretos usam o [webrtc-rs](https://github.com/webrtc-rs/webrtc) 0.21.1, com três ajustes (o terceiro, a parte pós-quântica do DTLS, está em "Privacidade"):
  - **O primeiro recado de um canal**: o `rtc` 0.21.1 (o núcleo do webrtc-rs) às vezes perdia a primeira mensagem de um canal de dados combinado de antemão (`negotiated`), como o de controle das chamadas e o dos arquivos diretos. Quando ela chegava junto com o fim do aperto de mão do SCTP, no lado que sobe por último, ia para o canal antes do evento que o abre, achava o canal fechado e era descartada (`ErrDataChannelNotExisted`), embora o SCTP já tivesse confirmado o recebimento; ninguém mandava de novo. Nas chamadas, eram os recados que saem quando o canal abre (os codecs, a cópia do vídeo que cada um quer, o som da tela, as apresentações e as anotações); nos arquivos diretos, o pedido. O app usa uma cópia do `rtc` com a correção (`vendor/rtc`, no lugar do publicado pelo `[patch.crates-io]` do `Cargo.toml`): os dados de uma associação que acabou de subir esperam no SCTP até o evento passar, e seguem logo atrás dele, na mesma volta do laço. Entre duas cópias do app neste PC, cada lado mandando um recado no instante em que o canal abre, 7 de 100 conexões perderam um sem a correção; com ela, nenhuma de 100, no build de debug e no otimizado. Os 283 testes do `rtc` passam, e dois deles, que reproduzem a perda, falham sem a correção. Ela vale para quem recebe: uma cópia do app anterior a esta ainda perde o que chega a ela. A mesma correção, com os testes, foi enviada ao webrtc-rs ([rtc#292](https://github.com/webrtc-rs/rtc/pull/292)), mas o app não depende disso: todo build dele já usa a cópia corrigida, seja qual for a decisão de lá. A pasta fica também porque o `rtc` dela passa ao DTLS o segredo pós-quântico (veja "Privacidade").
  - **Buffers UDP**: o Windows dá 64 KB a cada socket UDP para guardar o que chegou e ainda não foi lido, e o que passa disso é descartado antes de o WebRTC ver: numa rajada de vídeo, um pacote perdido custa um NACK ou uma imagem inteira; num arquivo direto, uma retransmissão e uma janela menor do SCTP. Os sockets das chamadas, dos arquivos diretos e do relé local (o de TCP e TLS) pedem 4 MiB para receber e para enviar (`crates/app/src/voice/udp.rs`), como os navegadores e as pilhas de QUIC fazem (o Chrome pede 256 KB nos sockets de vídeo, o quic-go uns 7 MB). É um teto, não memória reservada: o Windows só guarda o que chegou. No app otimizado, entre duas cópias neste PC, 400 MiB pelo canal de dados foram a 108 a 149 MB/s, contra 52 a 89 MB/s com o padrão do Windows; um arquivo direto inteiro, conferido e gravado, a 72 a 76 MB/s, contra 21 a 41 MB/s, e com o padrão um deles chegou a parar.
- **Voz e vídeo no app**: a voz passa por cancelamento de eco e ganho automático ([sonora](https://crates.io/crates/sonora)) e pela supressão de ruído escolhida (abaixo). Em Configurações → Voz e vídeo dá para escolher o microfone e a saída de áudio (sem escolha, os padrões do Windows); a saída vale para as chamadas, os sons do app e os anexos, e a troca vale na hora, no meio de uma chamada também. Um aparelho escolhido que for desconectado dá lugar ao padrão do Windows até voltar. O microfone e a saída abrem e fecham em threads só deles: fechar um aparelho deixa a thread no modelo de COM de thread única (é o que o cpal faz), e numa thread do runtime, que todas as tarefas dividem, isso ficava, e o próximo que pedisse o outro modelo (o som da tela, o codificador da placa, um vídeo) falhava com `RPC_E_CHANGED_MODE`. Esses, por sua vez, aceitam a thread no modelo em que ela já estiver, como acontece quando um programa de áudio de terceiros se injeta no app. Dá para escolher qual tela ou janela compartilhar (com miniaturas), pela captura de tela do Windows, e a câmera vem pelo Media Foundation. Quando a placa de vídeo tem um codificador (NVENC, Quick Sync ou AMF), a imagem da tela não sai dela: a placa reduz a imagem para cada cópia e codifica em H.264 ou AV1 (`crates/app/src/voice/hw.rs`), e o quadro de quem compartilha é desenhado direto dessa imagem quando a interface desenha na mesma placa. Se a placa parar de codificar no meio, o compartilhamento segue pelo processador sozinho, depois de uma pausa de pouco mais de um segundo. A câmera, e a tela num PC sem codificador na placa, vão pelo openh264, no processador. O AV1 que chega é decodificado no processador, com o [rav1d](https://github.com/memorysafety/rav1d). As imagens (da captura, das cópias menores, das que chegam e dos vídeos que tocam) são escritas sobre a memória das anteriores, assim que a interface termina de usá-las: uma imagem nova de 3 a 8 MB por quadro vinha do Windows como páginas novas, e só isso custava alguns por cento de um núcleo.
  - **Supressão de ruído** (Configurações → Voz e vídeo, e a troca vale na hora, no meio de uma chamada também): "IA", a que vem escolhida, é a rede neural [DPDFNet](https://github.com/ceva-ip/DPDFNet) (Ceva, dezembro de 2025, [artigo](https://arxiv.org/abs/2512.16420)) na versão de 48 kHz com dois blocos de caminho duplo; entre os modelos causais abertos, o artigo dela a mede, no geral, acima do DeepFilterNet2 e 3, do GTCRN, do DPCRN, do DEMUCS e do CleanUNet. Ela fica entre o cancelamento de eco e o ganho (que vem depois, para subir a voz e não o ruído) e roda dentro do .exe pelo [tract](https://github.com/sonos/tract), em Rust puro, sem DLL; o modelo vai no próprio app (`crates/denoise`, 5,3 MB com os pesos guardados em float16; a diferença na saída fica mais de 60 dB abaixo do som). Custa atraso: a rede devolve o som 50 ms depois (10 da janela de 20 ms e 40 do quanto o modelo olha adiante), e no `cargo xtask medir voz` a voz foi da boca ao ouvido em 123 ms, contra 73 ms com a padrão. E custa processador: 2,2 ms a cada 10 ms de som num Ryzen 7 5700X3D (o app inteiro numa chamada foi de 16 para 37 % de um núcleo), mais uns 30 MB de memória e 28 MB no .exe (o tract e o modelo); com o microfone mudo ela descansa. Em fala de verdade com ruído (o [conjunto de avaliação do DPDFNet](https://huggingface.co/datasets/Ceva-IP/DPDFNet_EvalSet): escritório, bar e rua, em português), as pausas ficaram 38 a 68 dB abaixo da voz, contra 10 a 17 dB com a padrão e 4 a 10 dB sem nenhuma. A rede é lida na primeira chamada (um quarto de segundo, longe do áudio), e a chamada usa a padrão até ela ficar pronta; se o PC não der conta dela a tempo (mais de 6 ms a cada 10 ms, em média), a chamada segue com a padrão e o app avisa. "Padrão" é a do WebRTC, a dos navegadores; "Desligada" manda o som como o microfone pega.
- **Interface**: só redesenha quando algo muda, e nunca mais rápido que a tela (o vsync não segurava: uma animação chegava a 1.400 quadros por segundo). Usa o Direct3D 12 quando o PC tem placa de vídeo para ele (`WGPU_BACKEND` escolhe outro) e pede ao wgpu blocos pequenos de memória: com o padrão do wgpu e todos os backends ligados, o app aberto num canal ocupava 390 MB de memória privada (145 MB no Gerenciador de Tarefas); agora, 170 (75).
- **Anexos de áudio e vídeo** tocam dentro do app. O áudio é lido do servidor aos pedaços enquanto toca e decifrado na memória (começa na hora, de qualquer tamanho); um vídeo cifrado baixa inteiro primeiro, decifrado, para `%TEMP%\babutela-midia`, porque o Media Foundation lê o arquivo sozinho e não saberia decifrá-lo, e o arquivo é apagado quando o player fecha (os vídeos antigos, sem criptografia, ainda são lidos aos pedaços do servidor): áudio com [symphonia](https://crates.io/crates/symphonia) e Opus (MP3, M4A, AAC, OGG, Opus, WAV, FLAC), vídeo pelo Media Foundation do Windows (MP4, MOV, WebM, MKV, AVI, WMV, com os codecs que o Windows tiver), com a imagem na conversa e uma visão ampliada. O vídeo é decodificado e convertido para RGB na placa de vídeo (DXVA), e só a imagem pronta vem para a memória: um vídeo 720p a 30 quadros por segundo passou de 22 a 27 % de um núcleo para 7 a 10 %, e de 240 MB para 206 MB na RAM. Se a placa não abrir o vídeo, ele toca pelo processador, como antes.
- **Mensagens** de até 100 mil caracteres e até 100 anexos. Uma mensagem longa aparece pelo começo, com "mostrar a mensagem inteira".
- **Menções**: digitar "@" na caixa de texto abre a lista de quem está na conversa (os membros do servidor, ou a outra pessoa numa conversa direta), filtrada pelo que vem depois, pelo nome ou pelo nome de usuário, sem diferença de maiúsculas e acentos. As setas escolhem, Enter, Tab ou um clique põem "@usuário" no texto, e Esc fecha a lista. Na mensagem, a menção aparece com o nome da pessoa ("@Beto") e abre o perfil dela com um clique. Quem é mencionado vê a mensagem destacada e, em outra conversa, recebe o som e a notificação, e o canal ganha o número vermelho. O texto leva o nome de usuário, então as versões anteriores do app também reconhecem a menção.
- **Servidores**: quem gerencia o servidor troca a imagem dele nas configurações (o app a reduz para um quadrado PNG de 256 px antes de enviar; ela fica no R2 como os anexos, e a anterior é apagada) e pode deixá-lo privado. Num servidor privado o convite só faz um pedido de entrada, que quem pode expulsar membros aceita ou recusa em "Pedidos de entrada", no menu do servidor; o número de pedidos aparece ao lado do nome dele. Quem pediu vê o pedido no "+" da barra de servidores, onde pode cancelá-lo, e recebe um aviso quando é aceito ou recusado. O "+" de cada categoria cria ali um canal do tipo dela (de texto ou de voz) pedindo só o nome; o "Criar canal" do menu pede o tipo, o nome e a categoria.
- **Emoji**: o seletor (o do botão do chat e o das reações) tem a lista inteira do Unicode, não uma lista fixa no app, com busca em português, as categorias, o tom de pele e os usados por último.
  - A lista, a ordem, as categorias e os tons vêm do [`emoji-test.txt`](https://www.unicode.org/Public/emoji/latest/emoji-test.txt) do Unicode, sempre a versão mais nova (hoje a 18.0). É a fonte oficial ([UTS #51](https://www.unicode.org/reports/tr51/)): a do Google ([emoji-metadata](https://github.com/googlefonts/emoji-metadata)) sai dela e anda atrás (ainda na 17.0). Os nomes e as palavras da busca vêm do CLDR em português ([cldr-json](https://github.com/unicode-org/cldr-json), também do Unicode), fixado numa versão publicada (49.0.0, a primeira com os nomes do Emoji 18.0; `babutela_buildinfo::emoji`). Sem os nomes, o seletor funciona com os nomes em inglês.
  - O app lê os três arquivos da cópia que o nosso servidor guarda (`<servidor>/emoji/`, no R2), que o `cargo xtask emoji` copia dos endereços oficiais (o `release update` faz isso também). Assim o PC de quem usa só fala com o nosso servidor. Enquanto o servidor não tem a cópia, o app busca direto no Unicode e no GitHub. Os arquivos ficam em `cache\emoji`; depois de 7 dias ele só pergunta se mudaram (ETag e Last-Modified), no mesmo lugar de onde veio a cópia. Um arquivo que não é o que diz ser (a página de um proxy, um erro respondido como 200, um arquivo pela metade) nunca substitui a cópia guardada. Sem internet, usa a cópia guardada, por mais velha que seja; sem cópia nenhuma, o seletor avisa e oferece "Tentar de novo". A lista é lida 8 segundos depois de o app abrir, ou quando o seletor abre, se for antes.
  - Todos os emoji aparecem inteiros e coloridos, no seletor e nas mensagens (veja "Emoji colorido"). O app confere cada um com as fontes que vai usar e guarda a resposta (`visiveis.json`, com qual fonte desenha cada um) até a lista, as fontes do Windows ou a versão do app mudarem; a conferência roda longe da janela, uma vez só (3 s no build de teste). Num Windows 11 (build 26300) com a 18.0, aparecem os 1.923 (332 com tons e 19 com um tom para cada pessoa) e nenhum fica de fora. Um emoji que nenhuma fonte desenhe inteiro, como o de uma versão futura antes de o app ter a fonte dela, some do seletor.
  - Um tom de pele vale para todos os emoji que têm tons (o botão da mão, ao lado da busca, como no Discord). Os emoji de duas pessoas (aperto de mão, casais, beijo, de mãos dadas, orelhas de coelho, luta) também aceitam um tom para cada pessoa: o botão direito sobre um deles abre uma grade de 5 × 5 (a linha é o tom da primeira pessoa, a coluna o da segunda, como no Gboard), com a última combinação escolhida em destaque, e "Voltar" ou digitar na busca devolve a grade de emoji. O tom e os 27 usados por último ficam em `prefs.json`.
  - A busca acha pelo começo das palavras, sem ligar para acentos ("coracao" acha "coração"), primeiro pelo nome e depois pelas palavras-chave do CLDR; Enter escolhe o primeiro. Com o mouse em cima, o nome do emoji aparece embaixo, com os tons ("aperto de mãos: pele clara e pele escura").
- **Figurinhas do GIPHY**: o botão ao lado do emoji abre a busca, as "Em alta" e as "Favoritas". Um clique envia a figurinha como mensagem (sozinha, sem texto; dá para responder com ela, não para editá-la); a estrela, no seletor ou sobre uma figurinha no chat, guarda ou tira das favoritas (até 100 por pessoa, no servidor, então valem em todos os dispositivos). As regras do GIPHY decidem o desenho:
  - O app fala com o GIPHY direto, e baixa as imagens de lá; nada passa pelo nosso servidor.
  - O servidor guarda só o id de cada figurinha favorita, nunca os endereços das imagens nem as imagens; numa mensagem, o id vai dentro do envelope cifrado, e o servidor nem o vê. Cada app pergunta ao GIPHY, uma vez por sessão, como é cada id (até 100 ids num pedido só).
  - Os resultados aparecem na ordem do GIPHY. O seletor mostra a marca oficial "Powered by GIPHY" com o logo (a versão para fundo escuro do kit do GIPHY, `crates/app/assets/giphy/`), e cada figurinha mostra, com o mouse em cima, o título e quem a criou ("Por Nome (@usuário) no GIPHY"), como os termos pedem.
  - O app avisa o GIPHY quando uma figurinha é vista (no seletor e no chat), clicada e enviada, com um identificador que é um hash da conta, não a conta.
  - Quando o GIPHY está com problemas ele responde "200" vazio; o app trata isso como falha e tenta de novo depois, em vez de achar que as figurinhas sumiram.
  - Classificação até PG-13 e buscas em português.
  - Para gastar poucos pedidos da chave: a busca espera a digitação parar (400 ms, a partir de 2 letras), as páginas vêm conforme a grade rola (24 por vez), as "Em alta" só são pedidas de novo depois de 10 minutos e os ids de uma conversa inteira vão juntos.
  - As animações (WebP, com fundo transparente) ficam só na memória, nunca em disco: cada uma vira uma textura só, com os quadros lado a lado, no tamanho em que aparecem (com uma textura por quadro, 35 figurinhas eram 700 texturas, e o driver da placa segurava uns 170 MB a mais para 20 MB de imagens; com uma por figurinha, uns 50 MB), com até 120 quadros e 16 MB por figurinha (com 40, uma figurinha de 15 segundos mostrava um quadro a cada 375 ms; agora, a cada 125). Todas trocam de quadro no mesmo compasso, de 1/30 de segundo: cada uma no próprio ritmo, vinte figurinhas do GIPHY faziam a janela ser redesenhada 82 vezes por segundo; no compasso, são 30. Um compasso de 50 ms redesenhava 20 vezes, mas tirava cada quadro 17 ms do tempo dele (mediana), e as figurinhas de 15 quadros por segundo andavam aos trancos; com o de 1/30 s, 6,7 ms. Elas só se mexem com a janela na frente; no chat, uma figurinha se mexe por 8 segundos quando aparece e depois para no primeiro quadro, e volta a se mexer com o mouse em cima. As que ninguém desenhou por 20 segundos saem da memória.
  - A montagem dos quadros foi conferida contra a libwebp (a biblioteca de referência do WebP), quadro a quadro, em 94 figurinhas do GIPHY (282 arquivos, WebP e GIF): nenhuma diferença visível. Três cuidados saíram disso: o image-webp não limpa a área de um quadro marcado para ser descartado se não houver uma cor de fundo definida (sem isso, 42 de 96 arquivos deixavam restos dos quadros anteriores, em até 28 % da imagem), alguns arquivos trazem um véu branco quase invisível (alfa 2 de 255) que no fundo escuro do app virava uma caixa, e os quadros que sobram de uma figurinha longa são escolhidos pelo tempo, não pela contagem.
  - Medido com `cargo xtask medir figurinhas --giphy`, contra o GIPHY de verdade (42 figurinhas carregadas, 2 pedidos da chave por rodada): com o seletor aberto e tudo se mexendo, 3 % de um núcleo, 29 MB de texturas e uns 196 MB de memória privada; com o seletor fechado e duas figurinhas paradas no chat, 0,2 % e 4 MB de texturas.
- **Notificações**: clicar numa notificação abre a conversa, mesmo depois que ela foi para a central de notificações e mesmo com o app fechado. O Windows inicia o app pelo ativador COM registrado para ele.
- **Emoji colorido**: a fonte de emoji do Windows desenhada em cores, e as bandeiras por uma fonte própria, porque o Windows mostra bandeiras como letras. O egui (0.37) escolhe a fonte de cada emoji pelo primeiro caractere, e isso saía errado em três casos, que o app corrige antes das fontes (`crates/app/src/emoji_font.rs`, um `GlyphRasterizer` do epaint com `FontPriority::Highest`, consultado antes de qualquer fonte):
  - Teclas e símbolos com o seletor de emoji (#️⃣, 1️⃣, ©️, ™️, ♥️, ‼️, ↔️): o primeiro caractere (# ou ©) existe no Segoe UI, e eles saíam em preto e branco, na fonte do texto. A UTS #51 diz que o seletor U+FE0F pede o emoji, e os navegadores procuram uma fonte colorida nesse caso; no egui isso ainda está em aberto ([#8559](https://github.com/emilk/egui/issues/8559)). Agora vêm do Segoe UI Emoji. Sem o seletor (#, ©, ™, ♥), continuam texto.
  - Emoji que a fonte do Windows ainda não tem: os 9 do Emoji 18.0 no Windows 11 de outubro de 2026 (a [Emojipedia](https://blog.emojipedia.org/whats-new-in-unicode-18-0/) espera a 18.0 no Windows lá por setembro de 2027), e uns 600 no Windows 10, cuja fonte parou no Emoji 12. Saíam como quadradinhos ou em preto e branco, até nas mensagens de quem usa Windows 11. Agora vêm do Noto Color Emoji do Google (2.057, a fonte COLRv1 da 18.0), que vai no app: 4,8 MB no .exe, 2,2 MB a mais no instalador (`crates/app/assets/fonts/`, guardado em .xz; o build.rs abre). Esses poucos ficam no estilo do Google até o Windows ter os dele, e quando tiver o app passa a usar o do Windows sozinho.
  - A bandeira de Sark (🇨🇶, do Emoji 16.0), que a fonte das bandeiras não tem: também do Noto.
  - Cada emoji é conferido uma vez, montado a 8 px em cada fonte, e a resposta fica guardada: o resto do texto não muda (100 mil caracteres levaram 27,4 ms antes e 27,7 ms depois). As famílias (👨‍👩‍👧) e os casais de dois tons, que o Segoe UI Emoji monta com uma figura por pessoa, uma sobre a outra, já saíam inteiros e continuam pelas fontes do texto.
- **Instalador**: em Rust (`crates/setup`), com a janela de diálogo do próprio Windows. Instala para o usuário em `%LOCALAPPDATA%\Programs\BabuTela`, sem pedir administrador, cria os atalhos e o desinstalador. `/S` instala sem janela (a atualização da 0.11.1 e anteriores); `--update --wait-pid=N --relaunch [/S] [--minimized]` é o app se atualizando: espera o app fechar, troca o arquivo com uma janelinha de progresso (nenhuma com `/S`) e abre o app de novo, desse ou daquele jeito, deu certo ou não.
- **Atualização automática**, como a do Discord: a cada vez que abre, o app pergunta ao servidor se há versão nova antes de mostrar o resto (a tela de "Checking for updates" do Discord), baixa com o progresso na tela, confere as assinaturas (veja "Privacidade") e o SHA-256, instala e abre de novo já nela. Uma versão só é baixada depois de aparecer no registro público (veja "Privacidade"), que o app só lê com as chaves da conta prontas, depois de abrir: por isso uma versão que acabou de sair é baixada em segundo plano logo depois da abertura e entra na abertura seguinte. Com o app aberto, ele procura a cada 4 horas e baixa em segundo plano; a faixa avisa "Atualização pronta: ela entra quando o Babu Tela abrir de novo", com "Reiniciar agora", e a próxima abertura instala antes de qualquer janela, sem precisar da internet (é o que acontece ao ligar o PC com "Iniciar com o Windows", sem aparecer nada). Só a cópia instalada (a da pasta registrada em "Aplicativos") se atualiza sozinha, nunca um build de teste, e aberto por um clique numa notificação o app não troca de versão naquela hora. Três diferenças do Discord, de propósito:
  - O app fica sempre no mesmo arquivo, no mesmo lugar. O Discord instala cada versão numa pasta nova (`app-1.0.9xxx`, do Squirrel), o que perde os atalhos fixados na barra de tarefas e as regras do firewall a cada versão, e aqui o ativador das notificações e o "Iniciar com o Windows" também apontam para o arquivo.
  - Se o servidor não responde em 5 segundos, ou o download para por 30, o app abre na versão que tem e deixa a atualização para a próxima vez; "Abrir agora e atualizar depois" faz o mesmo na hora. O Discord fica tentando na tela de abertura até conseguir.
  - Uma mesma atualização é tentada por no máximo duas aberturas: se falhar nas duas, o app abre normalmente e fica o "Reiniciar agora".

No computador de quem usa ficam apenas, em `%APPDATA%\Prosa` (o nome antigo do app):

- `settings.json`, as configurações;
- `session.bin`, o login, criptografado com a chave do usuário do Windows;
- `chaves-<conta>.bin`: as chaves de ponta a ponta da conta, as das conversas e a identidade de cada pessoa como este PC a fixou, criptografadas do mesmo jeito (veja "Privacidade");
- `prefs.json`: a última tela aberta, a qualidade do vídeo, os sons desligados, o volume de cada pessoa, se o som do PC vai com a tela, o microfone e a saída de áudio escolhidos, o tom de pele dos emoji e os usados por último;
- `cache\`, as imagens já baixadas (as cifradas, como vieram do servidor), e `cache\emoji`: os três arquivos do Unicode, `fontes.json` (de onde veio cada um e quando foi conferido) e `visiveis.json` (o que este PC não desenha, e o que ele desenha com o Segoe UI Emoji ou o Noto à parte).

E, em `%LOCALAPPDATA%\Prosa\updates`, uma atualização baixada esperando a próxima abertura (o instalador e `atualizacao.json`, com a versão, o SHA-256 e quantas aberturas já a tentaram). Ela some depois de instalada, e o desinstalador apaga a pasta. Um anexo aberto fica decifrado em `%TEMP%\babutela-arquivos`, e um vídeo cifrado, enquanto toca, em `%TEMP%\babutela-midia`.

O endereço do servidor vem do build (`BABUTELA_SERVER_URL`, que o `cargo xtask release` preenche). Quem sobe a própria cópia do servidor pode escrever `"serverUrlOverride"` no `settings.json` à mão.

### Login com o Google

Não há senha: "Continuar com o Google" é o único jeito de entrar. É o fluxo que o Google indica para apps de computador ([RFC 8252](https://www.rfc-editor.org/rfc/rfc8252)):

1. O app abre a página do Google no navegador de quem usa, com um endereço de volta numa porta dele em `127.0.0.1` e um desafio PKCE.
2. Depois que a pessoa escolhe a conta, o Google manda o navegador de volta para essa porta com um código de uso único, e o app volta para a frente.
3. O app entrega o código e o segredo do desafio ao servidor, que troca os dois no Google com o segredo do cliente (`GOOGLE_CLIENT_SECRET`, que só o Worker tem) e recebe quem entrou.

Cada conta do Google é um usuário, achado pelo id que o Google dá a ela (o e-mail pode mudar). Na primeira vez o usuário é criado com o nome da conta do Google, e o nome de usuário vem do começo do e-mail. O e-mail só o dono vê, em Configurações → Conta; os outros veem o nome e o nome de usuário. Excluir a conta apaga tudo, e entrar de novo com o mesmo Google cria uma conta nova, vazia.

As contas da época das senhas foram apagadas uma vez só, na publicação da 0.11.0, com tudo o que tinham. Publicar uma versão nova (`cargo xtask servidor` ou `cargo xtask release update`) nunca apaga dados: o banco só ganha tabelas e colunas.

## Privacidade

O texto das mensagens, os anexos, as figurinhas, as respostas, as reações e a sinalização das chamadas e dos arquivos diretos saem cifrados e assinados do PC de quem envia, com chaves que só os PCs das pessoas têm (`crates/app/src/e2e/`). O servidor guarda e repassa o que não consegue abrir (`crates/worker/src/e2e.rs`). Quem tem a conta da Cloudflare (o Worker, o banco, o R2 e o relé TURN) e o cliente OAuth do Google manda no servidor, mas as chaves nunca passam por ele: não lê nada disso, e o que tentar além de ler (trocar uma chave, forjar, mudar, repetir ou mover uma mensagem, pôr um leitor a mais) o app recusa.

O desenho foi comparado com o dos mensageiros cifrados: o [MLS](https://www.rfc-editor.org/rfc/rfc9420) (RFC 9420, o padrão da IETF para grupos, que o [OpenMLS](https://github.com/openmls/openmls) implementa em Rust), o [DAVE](https://daveprotocol.com) do Discord (MLS nas chamadas), o [Megolm](https://gitlab.matrix.org/matrix-org/olm/-/blob/master/docs/megolm.md) do Matrix e o Signal. Ele fica mais perto do Megolm, que guarda o histórico cifrado no servidor e deixa relê-lo. O MLS apaga as chaves depois de usá-las (é o sigilo futuro dele), então um PC novo, ou o mesmo depois de reinstalar, não leria nada do que veio antes, e o Babu Tela guarda as conversas no servidor. As conversas com mensagens temporárias (abaixo) ganham o sigilo futuro: nelas as chaves também somem, de todos os PCs, alguns dias depois.

- **As chaves de cada conta**: uma identidade Ed25519, que assina tudo o que a pessoa manda, e uma chave X-Wing, para a qual os outros selam o que é dela, assinada pela identidade. O [X-Wing](https://datatracker.ietf.org/doc/draft-connolly-cfrg-xwing-kem/) junta o X25519 e o ML-KEM-768, o padrão pós-quântico do NIST ([FIPS 203](https://csrc.nist.gov/pubs/fips/203/final)): abrir o que foi selado pede quebrar os dois. Ele vem do [libcrux](https://github.com/cryspen/libcrux), cujo ML-KEM é o que o Signal usa; o resto (Ed25519, AES-256-GCM, HKDF e SHA-256) vem do `ring`, que o app já tinha pelo TLS e pelo WebRTC. Só as partes públicas vão para o servidor. No PC, as chaves ficam em `%APPDATA%\Prosa\chaves-<conta>.bin`, criptografadas com a chave do usuário do Windows (DPAPI), como o login.
- **Fixação e código de segurança**: na primeira vez que vê a identidade de alguém, o app a guarda, como o Signal e o SSH fazem. Se o servidor depois entregar outra, a conversa avisa ("A chave de segurança de Fulano mudou"), e nada vai para a chave nova até a pessoa aceitar; o que foi assinado com a antiga continua conferindo. No perfil de cada pessoa, "🔒 Código de segurança" mostra 60 dígitos feitos das duas identidades, os mesmos nos dois apps. Comparados pessoalmente ou numa ligação, eles mostram que ninguém está no meio, nem o servidor, e "Marcar como conferido" guarda isso.
- **Registro público de chaves** (a transparência de chaves da [verificação automática do Signal](https://signal.org/blog/key-transparency/) e do [keytrans](https://datatracker.ietf.org/wg/keytrans/about/) da IETF): toda chave que uma conta publica, e toda versão do app, entra numa lista no servidor que só cresce, e cada app guarda uma cópia inteira dela (`registro-<conta>.bin`, 57 bytes por entrada, encadeadas pelo SHA-256). Como a lista cabe inteira em cada app, não precisa das árvores de Merkle que uma lista de milhões pede (`crates/app/src/e2e/record.rs`). Três coisas saem dela:
  - o app só usa a chave que é a mais nova da conta na lista; uma de fora não recebe nada, e quem envia é avisado;
  - cada app vigia as entradas da própria conta e avisa quando aparece uma chave que ele nunca teve ("alguém tenta se passar por você");
  - as mensagens e a sinalização levam o tamanho e o hash da cópia de quem enviou, e quem recebe compara com a sua. Um servidor que mostrasse a uma pessoa uma lista com uma chave falsa e às outras a verdadeira é pego assim que as duas cópias se encontram, e também quando esconde de alguém entradas que outro app já tem ou muda uma entrada que um app já guardou: a conversa mostra o aviso em vermelho.
- **Mensagens**: cada PC tem uma sessão para cada conversa, uma chave aleatória de 256 bits selada com o X-Wing para cada leitor (quem pode ler a conversa, como o servidor diz) e para a própria conta, que é como os outros PCs da pessoa leem o que ela mandou. O servidor guarda as cópias seladas (`e2e_sessions`) e entrega a cada um só a dele. A sessão muda quando mudam os leitores (quem entra não lê o que veio antes, e quem sai não lê o que vem depois), depois de 7 dias e depois de 2.000 mensagens. Cada mensagem é um envelope com o id da sessão, um id aleatório e o conteúdo em AES-256-GCM, numa chave só dela (HKDF da chave da sessão com o id) e preso à conversa, à sessão e ao id. Dentro vão o texto, os anexos com as chaves deles, a figurinha, o trecho da mensagem respondida, a hora e a assinatura de quem escreveu, completados até um tamanho do [Padmé](https://arxiv.org/abs/1806.03160) e no mínimo 512 bytes, para o tamanho dizer pouco: as mensagens de até uns 300 caracteres ficam todas do mesmo tamanho. O servidor recusa uma mensagem sem envelope.
- **Mensagens temporárias**: o relógio no cabeçalho de cada conversa escolhe quanto as mensagens novas duram: desligadas, 1 dia ou 7 dias (numa conversa direta, qualquer um dos dois escolhe; num canal, quem gerencia canais). A hora de sumir vai assinada dentro do envelope: cada app tira a mensagem da tela nessa hora, e o servidor a apaga do banco, com as reações e os anexos, na limpeza seguinte. As chaves somem também. Nessas conversas a sessão dura um dia e vai selada para a chave X-Wing do dia de cada leitor, não para a da conta. As chaves do dia saem de uma catraca de hashes (a semente de cada dia é o SHA-256 da do dia anterior, e a de antes não se recupera), a mesma em todos os PCs da conta, e cada app publica a de hoje e a de amanhã. Cada PC apaga as chaves do dia com mais de 8 dias, e as sessões dessas conversas uns dias depois de as mensagens delas sumirem. Passado isso, nem o servidor, que pode ter guardado uma cópia do que devia apagar, junto com um PC roubado abre o que foi dito: é o sigilo futuro. Quem lê ainda pode copiar o texto ou fotografar a tela antes.
- **O que o app recusa**: uma mensagem adulterada, assinada por outra pessoa que não a que aparece como autora, levada para outra conversa, repetida pelo servidor (o mesmo envelope em outra mensagem) ou em texto claro numa conversa que já estava cifrada aparece como "⚠ Mensagem recusada", sem nada do que diz. Se o servidor contar mais alguém lendo uma conversa direta, nada é enviado. Num canal, quem o servidor conta como leitor mas não está na lista de membros do servidor, ou está sem a assinatura de um membro (abaixo), fica sem a chave.
- **Membros assinados**: num servidor, a entrada de cada pessoa é assinada por quem já estava (`crates/app/src/e2e/members.rs`). O dono assina a própria. Um convite novo é assinado por quem o criou, junto com a parte pública de uma chave feita de 32 bytes aleatórios que só o link leva (`CÓDIGO.SEGREDO`: o servidor vê o código, nunca o segredo), e quem entra assina a própria entrada com essa chave. Num servidor privado, quem aceita o pedido assina. E qualquer membro pode garantir alguém pelo perfil da pessoa. O app segue as assinaturas a partir do dono, e só quem elas alcançam recebe as chaves das conversas: uma conta que o servidor ponha na lista sozinho fica sem nada. Quem é o dono, o app guarda: o convite assinado diz (e quem entra por ele o fixa, num servidor privado assim que o pedido é aceito), e quem já estava fixa o da primeira vez que viu o servidor. Um dono diferente que o servidor diga depois não põe ninguém para dentro, e o app avisa (o servidor não reaproveita o número de um servidor apagado, e o dono nunca muda). Na passagem para isso, o app do dono garante uma vez os membros que já estavam; depois disso, quem entrar com um convite antigo (só o código) espera alguém garanti-lo.
- **Anexos**: cada arquivo ganha uma chave e é cifrado no PC antes de subir, em blocos de 64 KiB com AES-256-GCM (cada bloco leva o próprio número e a marca do último, então não dá para trocá-los de lugar, repeti-los nem cortar o fim), completado até um tamanho do Padmé, e sobe com o nome `arquivo.bin`. O nome de verdade, o tipo, o tamanho e a chave vão só dentro da mensagem: o R2 só tem bytes cifrados. As imagens e o áudio são decifrados na memória, e o `cache\` guarda as imagens como vieram, cifradas.
- **Reações**: o servidor só vê uma marca de cada emoji (16 bytes de um HMAC com uma chave da mensagem), para juntar e contar as iguais; o emoji vai cifrado e assinado por quem reagiu.
- **Chamadas e arquivos diretos**: a mídia já ia cifrada de um PC ao outro (o DTLS-SRTP do WebRTC), mas a sinalização passava pelo servidor em claro, e com ela a impressão digital do certificado DTLS de cada lado: trocando as duas, o servidor ficaria no meio da chamada. Agora cada recado (a oferta, a resposta e os candidatos) vai selado para a outra pessoa e assinado por quem mandou, com a chamada (ou o arquivo) e a hora dentro, e vale por 10 minutos. Um recado sem selo é descartado. O relé TURN só vê o tráfego cifrado. E o DTLS ganhou uma parte pós-quântica: cada lado põe 32 bytes aleatórios na sua descrição selada, e os dois juntos entram no aperto de mão ao lado da troca ECDHE (X25519, P-256 ou P-384), do jeito das suítes ECDHE_PSK da [RFC 5489](https://www.rfc-editor.org/rfc/rfc5489), que é o que a [RFC 8773](https://www.rfc-editor.org/rfc/rfc8773) faz no TLS 1.3 com um segredo de fora. As chaves dos canais de dados e as do SRTP passam a depender deles, e eles só viajam selados com o X-Wing: uma gravação da chamada (no relé TURN, por exemplo) continua fechada mesmo para quem um dia quebrar a troca ECDHE com um computador quântico. Se alguém trocar um deles no caminho, a conexão não sobe. A mistura está numa cópia do DTLS do webrtc-rs (`vendor/rtc-dtls`), e o segredo vem de `crates/app/src/e2e/dtls.rs`. O caminho padrão, a troca híbrida X25519MLKEM768 da [RFC 10024](https://www.rfc-editor.org/info/rfc10024/) (agosto de 2026) no DTLS 1.3 ([RFC 9147](https://www.rfc-editor.org/rfc/rfc9147)), ainda não está no webrtc-rs, que só fala DTLS 1.2.
- **PC novo**: as chaves são da conta, e vão de um PC da pessoa para outro sem o servidor poder abri-las nem trocá-las. O PC novo faz uma chave X-Wing só para isso e mostra um código de 16 letras e números (80 bits do SHA-256 dela). A pessoa abre o Babu Tela num PC onde já entrou, que pergunta "Aprovar um PC novo", e digita o código lá. Esse PC confere a chave com o código e sela para ela as chaves da conta e as identidades que fixou; o PC novo pede ao servidor a sessão de cada conversa quando a abre. O servidor só leva os dois recados (o `provision` do gateway, só entre as conexões da mesma conta) e não consegue pôr uma chave dele no lugar, porque o código não bateria. Por isso entrar na conta de alguém não basta para ler: quem entra num PC sem as chaves (com o Google, ou com uma sessão que o servidor criou) vê as mensagens trancadas, e os PCs da pessoa recebem um pedido de aprovação que ela não fez. Sem nenhum PC antigo, "Criar uma identidade nova" recomeça: o que veio antes não abre mais, e quem conversa com a pessoa é avisado de que a chave dela mudou.
- **Atualizações assinadas**: o `latest.json` leva assinaturas Ed25519 da versão, do nome e do SHA-256 do instalador, feitas com chaves que ficam no PC de quem as tem e nunca vão para a Cloudflare: a de `cargo xtask chave` e, com um `assinantes.txt` na raiz do repositório, as de outras pessoas. Esse arquivo diz quantas precisam assinar (`minimo = 2`, por exemplo) e traz uma chave pública por linha; cada assinante confere o instalador (o mesmo SHA-256 que o build dele deu) e manda a linha que `cargo xtask assinar <versão> <sha256>` mostra, que quem publica põe em `build/assinaturas/<versão>.txt`. Sem o arquivo, basta a chave deste PC. O app traz as partes públicas e só instala o que tem o mínimo de assinaturas de chaves diferentes da lista (e confere de novo antes de rodar o instalador baixado). Toda versão entra também no registro público, e o app só instala uma que está lá: uma versão feita para uma pessoa só teria de aparecer para todas. O servidor só aceita essa entrada de quem publica (um HMAC com o `PEPPER`). Assim, quem tem (ou invade) a conta da Cloudflare não consegue mandar uma versão que leve as chaves embora, e com vários assinantes nenhum deles, nem quem publica, assina uma sozinho.
- **Opções**, em Configurações → Privacidade: "Esconder meu IP" faz as chamadas e os arquivos diretos passarem só pelo relé TURN (o `relay` do ICE), e quem está do outro lado vê o endereço do relé, não o seu; vale para as conexões feitas dali em diante. "Mostrar quando estou digitando", desligado, não manda o "digitando…", e nem o servidor fica sabendo quando você escreve. O Worker não grava IPs, e o `cargo xtask servidor` o publica com os logs de pedidos desligados (Workers Logs e Logpush), que guardariam quem se conectou de onde e quando.
- **Tor dentro do app**: "Conectar pelo Tor", na mesma seção, faz tudo o que o app manda passar pela rede [Tor](https://www.torproject.org), e o servidor, a Cloudflare e o GIPHY veem o endereço de uma saída do Tor, não o seu. O Tor vem dentro do .exe: é o [Arti](https://arti.torproject.org), o Tor em Rust do próprio Tor Project (o crate `arti-client`), e não há nada para instalar (`crates/app/src/tor.rs`). As chamadas à API, os arquivos, as atualizações, a lista de emoji e o GIPHY vão por um proxy SOCKS5 do app (só em `127.0.0.1`, com usuário e senha aleatórios a cada abertura, e os nomes resolvidos na saída do Tor, nunca neste PC); o WebSocket e as conexões do relé TURN abrem circuitos do Tor direto. Como o Tor não leva UDP, as chamadas e os arquivos diretos vão só pelo relé, por TCP e TLS. O que ele aprende da rede fica em `%APPDATA%\Prosa\tor`, e a primeira conexão demora uns segundos (16 s neste PC, com o app otimizado), com o andamento na tela de "Conectando…"; as seguintes partem do que ficou guardado. Dois pedaços do Arti vão corrigidos em `vendor/` (veja "Estrutura"): sem eles, o Tor nunca conectava no Windows. Ligar ou desligar abre o app de novo. Se o Tor não ligar, o app pergunta antes de conectar sem ele. O login com o Google acontece no navegador, fora do app e fora do Tor.
- **Mensagens de antes**: as enviadas antes da criptografia, que o servidor podia ler, foram apagadas do banco na 0.12.0, com as reações, as denúncias e os anexos delas (`purge_plain`, em `crates/worker/src/db.rs`, uma vez só). A recuperação do Durable Object na Cloudflare ainda guarda o banco de até 30 dias atrás; depois disso, elas não existem mais. Um app anterior a esta versão não envia mais nada (o servidor responde que é preciso atualizar) e mostra vazias as mensagens novas; os apps se atualizam sozinhos ao abrir.

O servidor ainda vê, como em quase todo mensageiro cifrado, o que cerca as mensagens:

- as contas (o id e o e-mail do Google, o nome, o nome de usuário, a foto, o status e quando cada uma está online; o "Invisível" esconde isso dos outros, não do servidor), as amizades e os bloqueios;
- os servidores, os canais, os cargos e os membros, com os nomes, as imagens, os convites e quem assinou a entrada de quem;
- quem escreve em qual conversa e quando, o tamanho do envelope (já completado), quantos anexos uma mensagem tem e o tamanho deles (completado), quando ela é editada ou apagada, quem reage (não com o quê) e quem está digitando (a não ser com a opção desligada). Numa conversa de mensagens temporárias, isso sai do banco junto com a mensagem;
- o registro público, que todo app com conta recebe inteiro: os ids das contas e quando cada uma publicou uma chave;
- nas denúncias, quem denunciou qual mensagem e o motivo escrito; a mensagem continua cifrada, e a moderação a lê com as próprias chaves, se podia ler o canal quando ela foi enviada;
- quem está em qual chamada, com quem e por quanto tempo, e quem baixa qual arquivo direto de quem;
- os endereços IP de cada conexão: a Cloudflare vê todos (o Worker não os grava), e o relé TURN os de quem passa por ele; numa chamada direta, cada pessoa vê o das outras, a não ser com "Esconder meu IP". Com "Conectar pelo Tor", a Cloudflare e o relé veem só saídas do Tor;
- as figurinhas favoritas (os ids do GIPHY). O GIPHY vê as buscas, o IP e um hash da conta.

E o que ainda falta proteger:

- **As assinaturas contra um computador quântico**: o que vai selado (as mensagens, os arquivos, as chaves do PC novo e agora a mídia das chamadas e dos arquivos diretos) passa pelo X-Wing e continua fechado mesmo para um computador quântico no futuro. As assinaturas (das mensagens, dos certificados de membro e das atualizações) são Ed25519: um computador quântico grande poderia forjá-las dali em diante, sem abrir o que já passou.
- **O histórico das conversas sem mensagens temporárias** (o sigilo futuro, *forward secrecy*): nelas, para reler o histórico do servidor, as chaves ficam guardadas, como no Megolm. Quem tiver o `chaves-<conta>.bin` de um PC, aberto na conta do Windows da pessoa, e o banco do servidor lê tudo o que aquela conta podia ler nessas conversas. A chave X-Wing da conta não é trocada com o tempo. Numa conversa temporária, o que vazar de um PC só abre o que foi enviado nos 8 ou 9 dias anteriores.
- **O primeiro contato**: o registro público pega uma chave falsa mostrada a uma pessoa só, assim que ela troca uma mensagem com alguém que tem a lista certa, e a dona da conta vê qualquer chave publicada em nome dela. Ele não pega um servidor que mostre uma lista inteira falsa, e coerente, a um grupo que nunca troca mensagens com quem tem a verdadeira. Também não há auditores de fora: a comparação só acontece entre quem conversa. Conferir o código de segurança fecha isso de vez.
- **Quem são os membros**: a saída de alguém não é assinada. Um servidor desonesto pode deixar na lista quem foi expulso ou saiu, e essa pessoa continua recebendo as chaves; os outros só veem que ela continua na lista. O dono de cada servidor vem do convite assinado com que se entrou; sem ele (para quem já estava, e num servidor privado quando o app fechou antes de o pedido ser aceito), é fixado na primeira vez que o app vê o servidor, como as identidades. Quem entra com um convite antigo (só o código) não recebe nada até alguém garanti-lo.
- **O próprio app**: sem `assinantes.txt`, quem tem a chave das atualizações ainda pode publicar sozinho uma versão que leve as chaves embora; com vários assinantes, eles teriam de combinar. De todo jeito a versão fica no registro público, para todos: ninguém recebe uma versão feita só para si. Ainda não há build reproduzível, então o registro mostra que uma versão saiu, não que ela é o código deste repositório. A primeira instalação vem da página de download, no GitHub.
- **Os metadados**: o que está na lista acima. Esconder do servidor quem manda cada mensagem (como o *sealed sender* do Signal) ou quem é membro de quê pediria credenciais anônimas, que o app não tem. O Tor esconde o IP, não a conta: o servidor continua sabendo que é você.
- **Os arquivos no PC**: os anexos abertos ficam decifrados em `%TEMP%\babutela-arquivos` até o Windows limpar a pasta temporária.
- **As mensagens de antes**: apagadas do banco, mas guardadas por mais 30 dias na recuperação do Durable Object, que só quem tem a conta da Cloudflare alcança.

O libcrux entra só no X-Wing. Os avisos de segurança dele no [RustSec](https://rustsec.org) (no X25519 e no SHA-3, de 2025 e 2026) estão corrigidos nas versões do `Cargo.lock`, e um estudo de 2026 achou falhas até dentro da parte que ele diz verificada formalmente ([Kobeissi, eprint 2026/192](https://eprint.iacr.org/2026/192)): a verificação não é tomada como garantia. No X-Wing, uma falha só no ML-KEM ou só no X25519 não basta para abrir o que foi selado.

## Idiomas

O app fala português e inglês (`crates/app/src/lang.rs`). As traduções ficam em `crates/app/assets/lang/pt.json` e `en.json`, um arquivo por idioma, embutidos no `.exe` e lidos por chave — sem dependência nova (o `serde_json` que o app já usa). O português é o idioma de origem: uma chave que falte no catálogo em uso cai para o português e depois para a própria chave, então uma tela ainda não traduzida aparece em português em vez de em branco, e a migração acontece uma tela de cada vez sem nunca quebrar o app.

No código usa-se `t!("chave")` para um texto simples e `tf!("chave", nome = valor)` para um com `{nome}` dentro. O idioma atual é global: como o egui é modo imediato, trocá-lo redesenha tudo no quadro seguinte, sem nada a atualizar. A escolha fica em Configurações → Idioma e em `prefs.json`; na primeira vez o app segue o idioma da conta do Windows (português, ou inglês para qualquer outro). Um teste confere que os dois catálogos têm exatamente as mesmas chaves e os mesmos `{marcadores}`, então nada vai para o ar sem tradução. Um terceiro idioma é mais um JSON e mais um valor no enum `Lang`.

As telas já traduzidas: a de entrada (login, "Conectando…", "Atualizando"), Configurações inteira (com o seletor de idioma), os nomes dos sons, dos status e da supressão de ruído, e os diálogos do Tor. O resto da interface segue em português até ser migrado da mesma forma.

## Testes

- `cargo xtask testar`: os testes em Rust e, depois, 28 etapas de ponta a ponta contra o servidor publicado (32 com o R2 ativo), num banco só delas (`TEST_HUB`), com contas de teste que só existem lá. Elas cobrem o login (as rotas das senhas não existem mais, e o servidor fala com o Google, que recusa um código inventado), servidores (inclusive os privados: o pedido de entrada aceito, recusado e cancelado, e quem pode decidir), mensagens cifradas (o servidor guarda só o envelope, recusa a mensagem em texto claro e o envelope acima de 800 mil caracteres, e a reação vai pela marca), as chaves de ponta a ponta (cada conta publica só as suas, cada leitor recebe só a sessão selada para ele, e o pedido de um PC novo só chega aos outros PCs da mesma conta), figurinhas (dentro do envelope, e as favoritas que seguem para os outros dispositivos), arquivos diretos (no servidor, só o id do arquivo; os anexos inválidos recusados, e a sinalização só entre quem enviou e quem pode ler, recusada para quem não pode ler e para um arquivo que não está na mensagem), permissões, voz (a sinalização só entre quem está na chamada, e nada de SFU), amizades, limites e exclusão de conta, e, com o R2, o envio em partes (um arquivo de 17 MiB), a leitura por pedaços, o cancelamento e a imagem do servidor. Os testes do app falam com um GIPHY de mentira (`crates/app/src/giphy.rs`), sem gastar a chave, e baixam a lista de emoji de um servidor neste PC.
- `cargo xtask chamada`: abre de 2 a 6 cópias do app neste PC, numa chamada de verdade. No lugar do microfone, cada uma "fala" uma voz de teste (dois segundos falando, um calada). O teste confere a taxa da voz, que cada pessoa ouviu todas as outras e por onde (direto ou pelo relé).
  - `--pessoas N`: de 2 a 6 pessoas.
  - `--calado`: a última pessoa fica em silêncio, e o teste confere que quase nada sai dela (o DTX).
  - `--so-tcp`: só pelo relé TCP/TLS, como numa rede que bloqueia UDP.
  - `--tela` ou `--janela "Título"`: Ana compartilha a tela ou a janela. Beto amplia a imagem e tem que receber a cópia grande, Caio vai para um canal de texto e não recebe nada, e os outros ficam nos quadrinhos, com a cópia pequena. O som do PC vai junto: um tom baixo que o próprio teste toca (num processo do PowerShell, e a Ana pega só o som dele, ou cada cópia pegaria a chamada das outras). Todos têm que recebê-lo menos o Caio, que silenciou a transmissão antes de entrar, e para quem a Ana nem deve mandar. O Beto fica com o menu da Ana aberto (o do botão direito), que aparece na imagem dele.
  - `--placa`: como `--tela`, com as medições do app ligadas (`BABUTELA_MEDIR=1`) e a tela pela placa de vídeo.
  - `--apresentar ARQUIVO`: Ana apresenta o arquivo (.pptx ou PDF) e vai para o slide 2. Na metade da chamada, todos têm que ter todos os slides e estar no dela, e a Ana tem que contá-los como enviados. Depois disso os outros vão sozinhos dois slides à frente e ampliam, o que aparece na imagem deles.
  - `--anotar` (com `--tela`, `--janela` ou `--apresentar`, e pelo menos 3 pessoas): anotações sobre o que a Ana compartilha. A Ana desenha uma seta, o Beto um traço de caneta, um retângulo e outro traço com o ponteiro, e o Caio entra depois disso. Na metade, todos têm que ter os quatro traços (o Caio também, que os recebe da Ana), e, compartilhando a tela, a janela da Ana sobre ela tem que estar à vista, com os quatro, e fora da captura. Depois a Ana deixa só ela anotar e desfaz a seta, e o Beto limpa os dele: no fim, ningu��m tem traço nenhum, e todos sabem que só a Ana anota.
  - `--segundos N`: quanto tempo a chamada dura, de 10 a 90 (20 se não disser).
  - `--exe CAMINHO`: usa um app já compilado em vez de compilar o de teste, por exemplo `target\release\babutela.exe`, o que vai no instalador.
- `cargo xtask direto`: compila o app otimizado (perfil `medir`: no build de debug o WebRTC passa só uns 2 MB/s) e abre duas cópias neste PC. A Ana anexa um arquivo de 200 MB de bytes aleatórios com "Enviar direto" ligado e envia, e fica aberta até ele sair inteiro; o Beto baixa, pausa na metade, continua e tem que terminar com o mesmo arquivo, byte a byte. O teste confere também que o anexo, como o app do Beto abriu a mensagem, só descreve o arquivo (sem endereço nenhum), por onde a conexão foi, e mostra a velocidade sem a pausa.
  - `--mb N`: o tamanho do arquivo, em MB.
  - `--so-tcp`: só pelo relé TCP/TLS, como numa rede sem UDP. Esse passa pelo TURN da Cloudflare e conta na franquia de 1.000 GB por mês.
  - `--exe CAMINHO`: com um app já compilado.
- `cargo xtask medir`: compila o app otimizado (perfil `medir`, o do instalador, mas incremental) e mede, contra o servidor publicado e num banco de teste: `mensagens` (só pelo servidor, por HTTP e pelo gateway, e de um app a outro: na tela de quem mandou e na de quem recebe), `ocioso` (o app parado num canal), `voz` (de boca a ouvido, com um bipe por segundo no lugar do microfone), `tela` (da tela de quem compartilha à de quem vê, com a hora desenhada na imagem), `midia` (um vídeo 720p tocando no chat, que o próprio app grava na primeira vez), `figurinhas` (o seletor aberto com as figurinhas se mexendo, depois fechado com duas no chat, e uma busca para a imagem; contra um GIPHY de mentira que o xtask roda neste PC, `crates/xtask/src/giphy_fake.rs`, com figurinhas animadas desenhadas por ele, ou, com `--giphy`, contra o GIPHY de verdade com a chave de `build/cloudflare.json`, gastando 2 ou 3 pedidos dela e guardando a imagem em `build/giphy/` para a revisão do GIPHY) e `arquivos` (64 MB subindo e voltando, conferidos byte a byte). Sem nada, mede tudo. `captura` só roda quando pedido: a tela inteira compartilhada de três jeitos na mesma chamada (a captura do Windows e a do DXGI, as duas com o openh264 no processador, e tudo na placa de vídeo), com as duas janelas por cima das outras e a hora desenhada na tela. `qualidades` também: a tela inteira pela placa em cada qualidade do seletor, primeiro sem ninguém assistindo (com um canal de texto aberto no lugar da chamada) e depois com alguém assistindo ampliado. `--env BABUTELA_TESTE_MIDIA=processador` toca o vídeo do `midia` pelo processador, para comparar. Os apps medem o que fazem (`crates/app/src/probe.rs`, só com `BABUTELA_MEDIR=1`) e o xtask lê do Windows o processador e a memória de cada um, quatro vezes por segundo. O processador é contado pelos ciclos que o processo rodou (`QueryProcessCycleTime`): a conta comum do Windows anda em passos de 15,6 ms e erra rajadas curtas, como as de uma interface que redesenha 20 a 30 vezes por segundo (num programa de teste, 0,6 % de um núcleo aparecia como 0,0 %, e 0,9 % como 1,1 a 1,9 %). Medidas antigas de uso baixo, feitas antes disso, podem ter saído baixas demais.
  - `--rotulo NOME` guarda os números em `build/medidas/NOME.json`, e `--comparar NOME` mostra a diferença para um arquivo de antes.
  - `--env NOME=VALOR` passa uma variável para os apps, para comparar ajustes (por exemplo `WGPU_BACKEND=vulkan`).
  - `--ruido ia|padrao|desligada`: a supressão de ruído da chamada do `voz` (sem isso, a do app, a IA).
  - `--segundos N`: quanto dura cada fase medida, de 5 a 120 (20 se não disser).
  - `--exe CAMINHO`: mede um app já compilado (o do instalador, em `target\release\babutela.exe`) em vez de compilar o do perfil `medir`.
  - O processador varia uns 3 a 5 pontos entre duas rodadas iguais; diferenças menores que isso não querem dizer nada.
  - As mensagens que enchem o chat antes de medir têm envelopes de mentira, porque o xtask não tem as chaves de ninguém: os apps as mostram como recusadas. As medidas de antes da criptografia, com o texto delas na tela, não se comparam direto com as de agora.
- `BABUTELA_EMOJI_DADOS=PASTA cargo test -p babutela -- --ignored the_real_lists --nocapture`: monta o seletor de emoji com os três arquivos de verdade (baixados na pasta) e as fontes deste PC, mostra quantos aparecem (e quantos com um tom para cada pessoa), quantos ficam de fora e quais, de que fonte vem cada um, quanto demorou e o que a busca "coração" acha, e confere que nenhum passa do tamanho que o servidor aceita numa reação (16 unidades UTF-16).
- `BABUTELA_RUIDO_AVAL=PASTA cargo test -p babutela -- --ignored real_noisy_speech`: passa fala de verdade com ruído pelas três supressões de ruído e mostra, para cada uma, quanto as pausas ficam abaixo da voz, o volume da voz e o atraso. A pasta tem pares `NOME_noisy.f32` e `NOME_clean.f32` (48 kHz, mono, float32 cru), por exemplo gravações do [conjunto de avaliação do DPDFNet](https://huggingface.co/datasets/Ceva-IP/DPDFNet_EvalSet) passadas para 48 kHz.
- O próprio app tem um modo de teste: `babutela.exe --smoke-report=ARQUIVO` abre, conecta, segue os passos de `PROSA_SMOKE_ACTIONS` (por exemplo `go:first-server|open:settings`), salva uma imagem da janela em `ARQUIVO.png` e um resumo em `ARQUIVO`. `BABUTELA_TEST_HUB=<TEST_HUB>:<nome>` usa um banco de teste em vez do de verdade, e `PROSA_USERDATA` um perfil separado. `BABUTELA_GIPHY_KEY` usa uma chave do GIPHY no lugar da do servidor (para testar uma antes de pôr no Worker), e `BABUTELA_GIPHY_URL` aponta para outro GIPHY (o de mentira). `BABUTELA_GOOGLE_AUTH_URL` troca a página do Google por uma de mentira no passo `google` (o app faz o papel do navegador), para um servidor de teste com `GOOGLE_TOKEN_URL` apontando para o mesmo Google de mentira. Com `BABUTELA_SETUP_TEST` (o modo de teste do instalador, com a pasta e o registro de mentira), uma cópia instalada nesse modo se atualiza sozinha mesmo num teste, e `BABUTELA_TESTE_ATUALIZAR_A_CADA=<segundos>` troca as 4 horas da busca em segundo plano. `hover:` e `click:` apontam e clicam como uma pessoa, num ponto (`click:400:300`) ou no que foi desenhado com um nome (`click:botao:Aceitar`, `click:engrenagem:geral`, `click:mais:Canais de voz`), e `keys:` e `enter` digitam no campo que tem o foco. No seletor de emoji: `pop:emoji` e `pop:react` (o da mensagem mais nova) o abrem, `wait-emoji:<segundos>` espera a lista, `emoji-search:<palavras>`, `emoji-tone:<0 a 5>` e `emoji-tab:<n>` buscam, trocam o tom e vão para uma categoria, e `click:emoji:<emoji>`, `click:emoji-aba:<nome>`, `click:emoji-tons` e `click:emoji-tom:<n>` clicam como uma pessoa (um emoji só pode ser clicado enquanto está à vista). `rclick:` clica com o botão direito (`rclick:emoji:🤝` abre a grade de um tom para cada pessoa), `emoji-pares:<emoji>` abre essa grade direto, e nela `click:emoji-par:<emoji>` escolhe uma combinação e `click:emoji-voltar` volta. `open:licencas` abre a janela de licenças. Numa chamada, `apresentar:<arquivo>` apresenta um .pptx ou PDF (`apresentar:fim` para), `slide:<n>` vai para o slide n, `share-tab:slides` abre a aba Apresentação do seletor, `tecla:<nome>` aperta uma tecla pelo nome do egui (`tecla:PageDown`, como um passador) e `roda:<pontos>` gira a roda do mouse onde ele está (`hover:slide` o põe sobre o slide de quem assiste). Ainda numa chamada, `maximizar` (ou `maximizar:off`) maximiza a janela, `tela-cheia:on|off` faz o que o botão de tela cheia faz, `parar-de-assistir:<nome>` e `assistir:<nome>` fazem o que os botões sobre a tela de alguém fazem, e `click:` alcança `quadro:<nome>` (o quadro da pessoa), `tela-cheia:<nome>` e `parar-de-assistir:<nome>` (sobre a imagem, com o mouse em cima) e `sair-da-tela-cheia` (na barra da tela cheia, enquanto aparece). No chat, `click:mencao:<nome>` escolhe alguém na lista do "@". O resumo traz `fullscreen`, `geometry` (onde estão a janela, a área de desenho e a tela, em pixels), `unwatched`, `zoomed`, `draft` e `mentionList`. Nas anotações, `desenhar:on|off` liga ou desliga a barra sobre a minha própria tela compartilhada (o que o botão "Desenhar", ao lado de "Compartilhar tela", faz), `anotar:<nome>` abre a barra sobre o que essa pessoa compartilha (`anotar:fim` fecha), `ferramenta:<nome>` (`vanish`, `pen`, `marker`, `arrow`, `rect`, `ellipse`, `text` ou `eraser`), `texto:<x>,<y>,<palavras>` escreve uma anotação de texto no ponto `(x, y)` (de 0 a 1) do que está aberto, e `cor:<0 a 7>` escolhem a ferramenta e a cor, `traco:<x>,<y>;<x>,<y>...` desenha um traço (de 0 a 1 na imagem), `arrastar:anotacao` desenha com o ponteiro, `desfazer`, `refazer` e `limpar:meus|tudo` fazem o que dizem, e `so-eu:on|off` decide quem anota o que eu compartilho. Nos arquivos diretos, `direto:on|off` liga o "Enviar direto" para os próximos anexos, `wait-direto-msg:<segundos>` espera chegar uma mensagem de outra pessoa com um arquivo direto, `baixar:<pasta>` baixa o mais novo nessa pasta (sem a janela de salvar), `pausar-direto` e `continuar-direto` pausam e continuam o download mais novo, `wait-direto-pct:<pct>:<segundos>` espera ele chegar a essa porcentagem, `wait-direto:<segundos>` espera não haver download andando, e `wait-servido:<n>:<segundos>` espera n envios inteiros dos meus arquivos; o resumo traz tudo em `direct`. `BABUTELA_EMOJI_URL` busca os três arquivos (`emoji-test.txt`, `annotations.json` e `annotationsDerived.json`) num outro endereço. Os passos existentes estão em `crates/app/src/smoke.rs`.

## Segurança

- Mensagens, anexos, reações e a sinalização das chamadas e dos arquivos diretos cifrados de ponta a ponta, a mídia das chamadas com uma parte pós-quântica, um registro público de chaves e de versões que os apps comparam entre si, membros assinados, mensagens temporárias com sigilo futuro e atualizações assinadas por chaves que não ficam na Cloudflare (veja "Privacidade").
- Login só pelo Google (veja "Login com o Google"): o servidor não guarda senha nenhuma, o segredo do cliente OAuth fica só no Worker, e o PKCE faz um código que vazasse no caminho não servir a mais ninguém. O app só aceita a volta do Google em `127.0.0.1`, com o `state` que ele mesmo mandou.
- Limites contra abuso (de ritmo, não de tamanho): mensagens, uploads, servidores, convites, amizades, figurinhas e denúncias. Os limites longos ficam no banco, então não somem quando o servidor dorme.
- Cada parte de um envio leva um bilhete assinado com o `PEPPER`, que vale 7 dias e só para aquele arquivo; o servidor confere o tamanho de cada parte e do arquivo pronto, e só aceita como anexo o que terminou de subir.
- Sessões expiram após 30 dias sem uso, e o servidor guarda só o hash de cada uma. Excluir a conta encerra todas.
- As contas de teste (`/api/test/session`) só existem no banco dos testes, com o `TEST_HUB`; no chat de verdade essa rota não existe.
- Sem CORS: uma página de outro site não consegue usar o servidor pelo navegador de quem a visita.
- Bloquear pessoas, denunciar mensagens (vai para a moderação do servidor) e excluir a conta.
- Anexos cifrados que não são imagem, áudio ou vídeo baixam decifrados para `%TEMP%\babutela-arquivos` e abrem no programa do Windows para o tipo deles; os antigos, sem criptografia, abrem no navegador. Links só abrem se forem `http` ou `https`.
- Arquivos diretos: o servidor só repassa a sinalização entre quem escreveu a mensagem e quem pode lê-la (sem bloqueio entre os dois), e só para um arquivo que está nela, até 600 recados por minuto. O arquivo vai cifrado (DTLS) de um PC ao outro, com a impressão do certificado na sinalização selada e assinada, e cada pedaço é conferido com o hash que a mensagem traz: nem o servidor, nem o relé, nem ninguém no caminho consegue ler ou trocar o conteúdo. Quem baixa só escreve dentro do arquivo que escolheu salvar.
- `build/cloudflare.json` guarda as chaves e nunca entra no git.

## Limites conhecidos

- Só para Windows.
- Criptografia de ponta a ponta (veja o que ela ainda não cobre em "Privacidade"): quem perde todos os PCs da conta perde o histórico, porque nenhuma cópia das chaves fica no servidor. Quem entra numa conversa não lê o que veio antes dele ("Mensagem cifrada sem chave neste PC"). Um vídeo cifrado só começa depois de baixado inteiro. As versões anteriores a esta não conversam mais: precisam se atualizar.
- Pelo Tor: tudo fica mais lento (cada pedido passa por três computadores pelo mundo), a primeira conexão pode levar minutos, e uma rede que bloqueia o Tor não conecta (o app então oferece abrir sem ele). As chamadas vão só pelo relé TURN, por TCP, o que atrasa a voz e conta na franquia do relé. O .exe fica maior, porque o Tor vai dentro dele.
- Mensagens temporárias: uma pessoa com todos os PCs fechados por mais de uma semana não recebe as que forem enviadas enquanto isso (não há chave do dia dela publicada), e quem envia é avisado; o tempo escolhido vale para as mensagens novas, não para as que já estão na conversa. "Esconder meu IP" precisa do relé TURN no servidor: sem ele, as chamadas e os arquivos diretos não conectam, e com ele contam na franquia do relé.
- O som da tela pede o Windows 10 versão 2004 (maio de 2020) ou mais novo; num mais antigo, a tela vai sem som e o app avisa. Uma janela de app da Microsoft Store (desenhada pelo `ApplicationFrameHost`) vai sem o som do app: para ele, compartilhe a tela inteira.
- O instalador não é assinado digitalmente, então o Windows mostra o aviso do SmartScreen. Resolver isso pede um certificado de assinatura de código.
- No plano grátis da Cloudflare cabem 100 mil pedidos por dia, 5 GB de banco e 10 GB de arquivos (o teto padrão de `armazenamentoGb`; passar disso custa US$ 0,015 por GB por mês, e baixar arquivos do R2 não custa nada). As chamadas não passam pela Cloudflare, a não ser entre duas pessoas que precisam do relé TURN. Só esse tráfego conta: 1.000 GB de saída por mês grátis, e US$ 0,05 por GB depois disso ([preços](https://developers.cloudflare.com/realtime/pricing/)).
- Um envio que o app não terminou (fechado no meio) e um arquivo que subiu mas não foi para nenhuma mensagem são apagados depois de alguns dias.
- Enviar direto: os dois precisam estar com o app aberto ao mesmo tempo, e só o PC que enviou tem o arquivo (não há outras fontes, como no BitTorrent: quem já baixou não repassa). Com esse PC desligado, ninguém baixa; mover, apagar ou mudar o arquivo nele faz os downloads pararem. Quem está invisível continua enviando, e quem baixa percebe que a pessoa está online. Quando os dois não se alcançam direto, o arquivo passa pelo relé TURN da Cloudflare e conta nos 1.000 GB grátis por mês (US$ 0,05 por GB depois): um arquivo de 50 GB pelo relé gasta 50 GB dela, para cada pessoa que baixa. A velocidade fica no que o WebRTC do app (webrtc-rs 0.21) aguenta: entre duas cópias do app no mesmo PC, de 72 a 76 MB/s (veja "Buffers UDP"); pela internet, normalmente o que a conexão de quem envia sobe. Não dá para baixar o próprio arquivo em outro PC da mesma conta (o servidor liga quem enviou a quem pode ler, não uma conta a ela mesma). Por enquanto foi testado entre cópias do app num PC só, não entre PCs e redes diferentes.
- Figurinhas: com a chave beta do GIPHY, 100 pedidos por hora valem para todos os usuários juntos. Gastam um pedido: abrir as "Em alta" (uma vez a cada 10 minutos por app), cada busca, cada página a mais da grade e cada conversa aberta com figurinhas novas; ver, clicar, enviar e as imagens não contam. Para um grupo pequeno costuma bastar (o próprio GIPHY diz que serve para a maioria dos apps); passando disso, o seletor avisa que o limite acabou por agora, e é hora da chave de produção, que o GIPHY concede depois de revisar o app e que tem custo. Uma figurinha que o GIPHY removeu aparece como "Figurinha indisponível".
- Apresentação: animações, transições, vídeos e sons dos slides não vão; cada slide aparece já completo, como no fim das animações dele. Os gráficos de um .pptx saem com os números certos, mas o BetterOffice (0.3, ainda antes da 1.0) ignora o estilo de cores do gráfico: o verde de um modelo pode virar as cores do tema, uma pizza 3D sai plana, e os números de um rótulo saem com ponto em vez de vírgula. Alguns efeitos tamb��m faltam (o reflexo de um texto, um fundo em gradiente). Para uma apresentação assim, salvar como PDF no PowerPoint e apresentar o PDF sai igual. As imagens têm até 1920 × 1080: ampliadas além disso, ficam menos nítidas. Fontes embutidas são desobfuscadas e usadas, mas um subconjunto pode faltar letras se a apresentação não embutiu todas. Arquivos .ppt antigos são convertidos pelo PowerPoint escondido se ele estiver instalado; sem ele, pedem para salvar como .pptx ou PDF. Numa chamada de N pessoas, quem apresenta manda N−1 cópias das imagens (uns 4 MB cada no modelo de 19 slides).
- Anotação: ainda sem carimbos nem notas adesivas, e não sobre a câmera. O texto digitado (botão "Texto" na barra, ao lado da elipse) é uma anotação de uma linha ou duas: Enter escreve, Esc cancela, e a cor e o tamanho vêm da própria barra. Quem usa uma versão do app anterior a esta não vê os traços nem desenha. Os traços sobre a própria tela de quem compartilha pedem o Windows 10 versão 2004 ou mais novo (o que deixa a janela fora da captura); num mais antigo, quem compartilha vê os traços só dentro do app. Desenhar direto na tela só foi testado num PC, numa tela 1080p a 100 %; com vários monitores ou outra escala, ainda não.
- Em malha, o upload de cada pessoa cresce com o tamanho da chamada. A voz cabe fácil: numa chamada de 6, quem fala manda uns 270 kb/s ao todo, e quem está calado quase nada. O vídeo se divide no que o upload de quem envia aguenta. Numa conexão fraca, todos recebem a cópia pequena antes de alguém receber a grande. Se nem a pequena cabe para todos, quem vem por último na fila vê só a foto.
- O chat (o Durable Object) fica no leste da América do Norte: a Cloudflare ainda não cria Durable Objects na América do Sul, e um pedido para lá cai nessa região ([documentação](https://developers.cloudflare.com/durable-objects/reference/data-location/)). Por isso uma mensagem leva de 120 a 130 ms de um app a outro no Brasil, uma ida e volta até lá; quem envia vê a própria na hora. As chamadas não passam por lá: vão direto entre as pessoas.
- Testado com até 6 cópias do app num mesmo PC, direto e pelo relé. Ainda não foi testado com muita gente em PCs e redes diferentes, nem com uma câmera de verdade a 60 fps.
- Música em grupo (botão da nota ao lado da engrenagem na chamada): o app baixa a música de um link do YouTube ou do SoundCloud e manda para todos na mesma faixa estéreo do som da tela, cifrada ponta a ponta como o resto. Quem colou o link é quem puxa (o DJ); se sair da chamada, o próximo da fila assume. A primeira música de cada PC baixa, uma vez só, o `yt-dlp` da [página de releases](https://github.com/yt-dlp/yt-dlp/releases/latest) (uns 24 MB, Unlicense) e o `qjs-windows-x86_64.exe` do [QuickJS-NG v0.17.0](https://github.com/quickjs-ng/quickjs/releases/tag/v0.17.0) (uns 2 MB, MIT, para resolver os desafios JavaScript que o YouTube pede), em `%USERPROFILE%\.babutela\yt-dlp\`, conferindo o SHA-256 contra o `SHA2-256SUMS` que o yt-dlp publica na mesma release; o yt-dlp mais recente é baixado uma vez por dia, para que correções do YouTube cheguem sem versão nova do Babu Tela. O que vai pela chamada é o áudio em Opus (96 kb/s estéreo); o vídeo nunca é baixado. Só links de `youtube.com`, `youtu.be` e `soundcloud.com` são aceitos. O YouTube e o SoundCloud não permitem retransmissão em grupo nos termos deles: a nossa aposta é a mesma dos "bots de música" dos servidores pequenos do Discord, com o detalhe de que o som sai do IP residencial do DJ (os IPs de datacenter da Cloudflare, do AWS e companhia o YouTube barra com "Sign in to confirm you're not a bot"). Nenhuma música é gravada: ela vive na memória do app do DJ enquanto toca.
- O compartilhamento de tela pela placa de vídeo (`crates/app/src/voice/hw.rs`) só foi testado numa NVIDIA RTX 5050, onde a placa codifica uma imagem 1080p em uns 2,2 ms em H.264 e 2,1 ms em AV1, contra 11 a 12 ms do openh264 no processador. Em placas Intel e AMD ainda não foi testado; se o codificador delas recusar o que o app pede, a imagem de teste feita antes de começar manda o compartilhamento para o processador. O AV1 é decodificado no processador de quem recebe (cerca de 1 ms por imagem 1080p, mais 0,85 ms para converter as cores, no PC da RTX 5050), ainda sem o decodificador de AV1 da placa. Trocar de codec no meio da chamada (quando entra ou sai alguém com uma versão anterior à 0.11.3) pede uma nova negociação e uma imagem inteira, e a tela para por cerca de um segundo. Telas HDR saem pela conversão para SDR que a captura do Windows faz.
